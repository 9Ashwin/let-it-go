# flow 不设审批闸门

`/prd`、`/to-design`、`/to-issues`、`/loop-it` 都**不等「回复 OK」**：产物落盘即视为可用，反馈当修订。
人只在两个地方被叫：`human_checkpoint`（判据是**危险面**，不是阶段）与**合入**（不可逆，归 `/merge-it`，
只有人能敲）——见 [CONTRACT §5](../skills/flow/CONTRACT.md)。

## 为什么不

审批闸门把澄清从连续过程切成瀑布：`问 → 写文档 → 等人批准 → 才敢继续`。真实的澄清是
`理解 → 做 → 观察 → 追问 → 调整`。闸门一立，第一步的「问」就会膨胀成一份要通读的清单，
因为每个人都知道只有这一次机会。

它还奖励错误的行为：等批准意味着**在拿到任何观测之前**就把方案定死，而
[CONTRACT §4](../skills/flow/CONTRACT.md) 的立场正好相反——判据落在已经拿到的观测上，
不落在事前信心上。

## 逃生通道

危险面本来就有停点，只是判据不是阶段：碰公开 API / 兼容性、数据迁移 / 破坏性变更、
权限 / 认证边界、不可逆 / 对外承诺时停一次等人（[CONTRACT §5](../skills/flow/CONTRACT.md) 的固定清单）。

有副作用的例外只有一处：真往**远端**建 issue、合 PR 之前先把清单摆出来——建出去再撤要费手脚；
写本地文件没有这个问题。

**问不到人不是失败**：工具列表里没有 `ask_user_question`（无人值守）、调用被拒（你是子代理）、
或人已经说了「怎么落地你定」——三种情况都自己定、写进工作状态、照常产出。
**停在「等你回复」上是唯一一定错的做法**：DSH 里 `turn_end: completed` 就是这个回合的终点。
这条有 T1 的机械断言守着（`no_human_wait`，负例见 `evals/harness/events_test.go`），
历史上真红过一次——iteration-9 的 `04-serial-batch/with_skill` 把批末评审派成后台子代理后停在 8/9。

## 历史上谁提过

- **issue #3 第一刀**：删掉审批闸门，`prd` 的「为什么不设评审闸门」与 `to-issues` 的盘问环节同时删。
- **loop-it / graph 收尾那轮**：确认 `run_in_background: false` 那条判断要留在正文里——后台子代理
  不会让本回合保持忙碌，等于用一个隐形闸门换掉显式闸门。
- **合入拆分那轮**：`/merge-it` 是这条规则唯一的例外形状——合入不可逆，所以把它拆成**只有人能敲**
  的一个技能（`disable-model-invocation: true`），而不是给 flow 加一道闸门。
