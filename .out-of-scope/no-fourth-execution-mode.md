# 执行模式只有三个

`单单元` / `串行批次` / `并行图` 是全部（[CONTRACT §3](../skills/flow/loop-it/CONTRACT.md)）。**不加第四种执行模式**
——包括「自动在三种之间切换的混合模式」「按规模自动升级」「按成本自动降级」这类包装。

## 为什么不

三种模式的差别是**仪式量**（差一个数量级），选哪一种的判据是**形态**：装不装得进一个上下文、
有没有真实阻塞边、节点之间真不真并行。这三条读输入就能判，不需要一个额外的模式来「管理」它们。

第四种模式的成本是实打实的：

- 它必须有**自己的判据**。判据一旦与现有三条重叠，就会出现「同一件事两个模式都声称负责」——
  那正是 issue #3 的病根（同一规则多处各写一遍）。
- 它必须有**自己的失败处理**（恢复、评审强度、交付落点），而这三样都已经按 profile 定义过一遍。
- 「自动切换」把一次可复核的判断藏进黑箱：事后没人能从产物里看出它当时选了哪条路。

## 逃生通道

- 形态拿不准 → 按判据读一遍输入；读不出来就按**更小的仪式**起步（单单元 → 批次 → 图），
  而不是发明一个中间态。
- 需要不同强度 → 调**评审强度**（按危险面）与 `--max-parallel`，不要加模式。
- 一批活里既有串行又有并行 → 拆成图（`/graph`），串行的部分就是一条链。
- 需要一个「只有人能敲」的动作 → 那是**调用轴**的问题（`disable-model-invocation`），不是执行模式
  ——`/merge-it` 就是这么来的。

## 历史上谁提过

- **issue #3 第一刀**：把「三个 profile」定成 flow 的唯一边界，取代此前散在七份 `SKILL.md` 里的
  多种说法。
- **loop-it / graph 收尾那轮**：讨论过「要不要给 `graph` 加一个自动降级到串行的模式」，结论是不加
  ——降级由编排器判（graph `SKILL.md` 的「判形态先于跑脚本」），不写成第四个模式。
