# to-design

## What it does

在有真岔口要留档时，写一份讲清**为什么这么选**的设计提案——重点是 Rationale 与 Compatibility，
不是长 SPEC。

它只在碰了固定清单上那几条之一时才该出现：公开 API、数据迁移（含改数据模型）、权限与认证边界、
兼容性、不可逆操作。判据是清单，不许自由心证；一条都没碰就别写。它也不承担字段级契约——表 /
接口 / schema 住在 [`/to-issues`](../../skills/flow/to-issues/SKILL.md) 的 issue 正文里；
Implementation 只写方向与过渡，不写细粒度步骤，因为 planner 写细了会级联出错。

## When to reach for it

**调用方式：** 你敲 `/to-design`，或者模型在任务对得上时自己伸手（没有 `disable-model-invocation`）。

该伸手的场合——碰了下面任何一条才用它：

| 判据 | 例子 |
|---|---|
| 公开 API | 改签名、改响应形状、加必填字段 |
| 数据迁移 | 改 schema、回填、删列 |
| 权限 / 认证边界 | 谁能做什么、token 生命周期 |
| 兼容性 | 旧调用方、旧数据、旧配置 |
| 不可逆操作 | 发布、删除、对外承诺 |

（与 [`../../skills/flow/loop-it/CONTRACT.md`](../../skills/flow/loop-it/CONTRACT.md) 第 5 节的危险面同源：那里是**停点**判据，这里是**留档**判据。）

与近邻的分界：

| 你手上是 | 该用哪个 |
|---|---|
| 一句还没成形的诉求 | [`/prd`](../../skills/flow/prd/SKILL.md) |
| 「为什么选这个方案、放弃了哪些备选」 | `/to-design` |
| 规格说明 / SPEC / 技术方案 | `/to-design`——`/prd-to-spec` 已并入这里 |
| 表 / 接口 / schema 这类字段级契约 | `/to-issues` |

## Common questions

**我只是想写份文档讲讲方案，不行吗？**
先问「这里有没有真岔口值得留档」，不问「要不要写文档」。没有 Rationale 的设计文档不值得写——把
已知的东西抄一遍不是产出。不适用的章节就删，删得显眼就说明原因。

**规格说明到底走哪个技能？**
走这里。这个词曾经挂在 `/prd` 上，结果是有人要 spec、却被带到写 PRD 的技能——那是一次真的误路由，
触发词已经改过来了。

**设计文档写完就冻结了吗？**
不是。契约在 issue 正文，设计文档不是契约：被实现证伪或已经过时，就直接重写或删掉，不要供着。
方案最终被否也照写——记录「这条路为什么走不通」本身就是产物，Status 标 Rejected。

**要不要写实现步骤？**
不写细粒度步骤，只写方向与过渡；实现该落在 issue 正文的验收条件上。

**HTML 页面是必经步骤吗？**
不是。Markdown 才是主产物，HTML 只是可选的呈现层，默认不渲染；用户明确要一份可分享、视觉固定的
页面时才用它。

## It's working if

- 每篇的 Rationale 里至少有一个被放弃的备选方案。
- 文档里找不到 `TBD` / `TODO`，也找不到细粒度实现步骤。
- 一条危险面判据都没碰的改动，没有产生设计文档。
- 有人要「规格说明 / SPEC / 技术方案」时，加载的是 `/to-design`。
- 文档和代码打架时，被改或被删的是文档。
- 被否掉的方案也留了档（Status 标 Rejected），而不是悄悄消失。
