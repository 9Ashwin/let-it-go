# graph

## What it does

把一件有**真并行度**的工作拆成有向无环的节点图，分层成波，每个波里互相独立的节点各自在一个 git worktree 里并发实现；波与波之间由 fan-in 屏障集成。

它和「把任务拆开、每个都派个 agent」的默认做法差在**收口的位置**：节点止于 commit——push、开 PR、merge、自审都不在节点里；泄漏检查、evidence 检查、集成、在集成后的树上跑门禁、评审一次、交付一次，全部收在波级。逐节点的 `/review-it` 是对一份可能活不过集成的 diff 的自审，逐节点的 `/ship-it` 意味着 N 个 PR、N 次 CI、N 次卡在 merge 冲突上的机会。节点只在自己的 worktree 与分支上工作，编排器持有波屏障，这是隔离与合并顺序能成立的前提。

工作状态、证据层与产物落点见 [flow 契约](../../skills/flow/CONTRACT.md)；本页只讲选它时要判的事。

## When to reach for it

**调用方式**：frontmatter 没有 `disable-model-invocation`——你敲 `/graph`，或者模型在任务对得上时自己伸手。

**触发边界**：两个及以上互不依赖、也不改同一段逻辑的单元。判据是**形态**，读输入就能判，不需要先跑规划器：

| 形态 | 该用 |
|---|---|
| 一个单元，整个改动装得进一个上下文 | 直接内联，或 `/loop-it` 的单单元路径 |
| 一批 issue 之间有真实阻塞边、要串行推进 | [`/loop-it`](../../skills/flow/loop-it/SKILL.md) 的串行批次 |
| 两个单元共享文件，或分层链（schema → API → UI） | `/loop-it`：那是链，不是图 |
| 节点之间真独立（互不共享文件，能各自 worktree 隔离） | **`/graph`** |
| 只有一句诉求、落地方案还要自己定 | 先 `/prd` → `/to-issues`，再回来 |

**判形态先于跑脚本**：`plan` 一写检查点就自动渲染看板，所以误用会在工作树里留下 `.graph_state.json` 与 `graph.html`——它们是派生物，不是成果，删掉。与 `/to-issues` 的分工也在这里：`/to-issues` 产卡片，`/graph` 直接吃任务、PRD/SPEC 或已有的 issue 集合。

## Common questions

**三个小任务，开张图是不是更稳？**
不。每个子代理整个生命周期都要付父级的完整 system prompt、工具 schema 和技能目录，一个琐碎节点花的远多于它省的。图的价值全部来自波内节点的真独立，不是来自「并行」这个词。

**两个节点会碰同一个文件，怎么办？**
共享的**接线文件**（router、`main`、路由表、DI 容器、type union）列进 `hot_files`，不要列进 `scope`——列进 `scope` 会把整张图串行化成一条链。规划器只在同一个波里两个节点声明了同一个 hot file 时告警，因为「只追加的改动能干净合并」这个前提对共享 import 块或路由表并不成立——那不是 merge 事故，那就是这次改动的形状，代价是同一个冲突被解三遍。

**为什么每个节点要单独一个 worktree？**
两个节点在同一个检出里实现会互相破坏，而失败模式是静默的。节点里的相对路径会解析到编排器的检出，所以节点内必须用绝对路径——这条纪律守住的证据，就是合并前共享检出上那次干净的泄漏检查。

**跑了一半要加节点、挪依赖呢？**
用 `--keep-shipped --only-pending` 重规划；**只要上次规划后又有节点交付，就在下一个波之前重规划**——最宽的布局不是开跑时算出来的那个。已交付节点若仍占着文件，整条尾巴会被静默压成每波一个节点。

**节点报告 `shipped`，为什么还要再核一遍？**
返回的对象是节点自己的**声明**，不是 evidence。泄漏检查、`files` 清单与它自己 diffstat 的对照、以及集成后的门禁，才是验证这个波的东西。集成后的门禁失败时以集成为准——节点测的是它的 worktree，不是组合。

**能不能每个节点一个可评审的 PR？**
可以，但那是昂贵模式：用之前先说清楚并确认。默认每波只评审与交付一次。

## It's working if

- 仓库里出现 `.graph-worktrees/node-*`，每个节点一条 `feat/node-*` 分支；节点分支上只有 commit，没有 push、没有 PR。
- 集成点是**一个** merge 提交同时含两条节点分支的祖先——那是「两个节点同属一波」的证据。
- 合并前共享检出是干净的（`git status --porcelain` 为空），没有节点逃出自己的 worktree。
- `graph.html` 是当前状态而不是几小时前的快照；你看得懂谁在跑、谁已交付，不用打开 `SKILL.md`。
- 失败的节点：worktree 留着、状态是 `failed`、依赖它的节点是 `blocked`，波里其余部分照常交付——不是整波重来。
