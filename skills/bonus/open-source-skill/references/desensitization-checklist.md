# 脱敏检查清单

发布公开仓库前逐条走完。**顺序不能反**：先列词表 → 再逐类替换 → 最后机械确认 0 命中。
凭记忆 grep 只能抓到你还记得的词，所以第一步必须是"把词写下来"。

## 第 1 步：列词表

把待公开的仓库通读一遍，对下面每一类写出**实际出现过的具体值**（不是类别名）。这张表就是后面 grep 的输入。
词表本身就是产物：下一次改版、下一次同步开源副本时，直接拿它重跑。

## 第 2 步：逐类处理

| 类别 | 找什么 | 换成什么 | 为什么危险 |
|---|---|---|---|
| 内部仓库 / 产品名 | 内部仓库名、项目代号、未公开产品名 | 通用说法（"源仓库"）或删除 | 外人最先搜到的内部信息，直接暴露组织边界 |
| 内部文件路径 | 只有内网才有的路径、私有目录结构、内部文档链接 | 相对路径，或删除 | 路径本身就是组织信息 |
| 人名 | 同事真名、作者真名、课程作者、评审人 | 角色名（"评审者"） | 个人隐私；也是把内容关联回来源的线索 |
| 内部编号 | 规则号、讲次号、工单号（如 `R013`） | 通用编号（`RULE-001`），或按 SKILL §4 的取舍决定去留 | 编号是内部系统的身份，可被反查 |
| 内部技能 / 工具名 | 只在内网存在的 skill、CLI、平台名 | 通用说法（"发布技能"） | 同样可反查，而且外部读者根本无法理解 |
| 凭据 | token、key、cookie、webhook secret、`.env` 内容 | 删除；历史里出现过的走轮换 | 最高危：一公开就等于失控 |
| 内网地址 | IP、内网域名、VPN 主机、私有 registry、内部 API 端点 | 占位域名或删除 | 直接给出攻击面 |
| 真实数据 | 用户 ID、订单号、邮箱、手机号、聊天记录 | 抽象形态（如 `user-12345`） | 个人数据，合规问题 |
| 内部黑话 | 只有内部人懂的缩写、流程名、项目简称 | 平实说法或删除 | 读不懂，且泄漏组织习惯 |

## 第 3 步：机械确认（期望 0 命中）

```bash
# 当前工作树
grep -rniE '<词1>|<词2>|<词3>' . --exclude-dir=.git

# 全历史对象：删掉的文件仍然躺在历史里
git grep -niE '<词1>|<词2>' $(git rev-list --all) -- 2>/dev/null | head

# 文件名与目录名本身就是泄漏面
find . -path ./.git -prune -o -name '*<内部词>*' -print
```

大小写不敏感还不够：内部词常出现在**文件名、目录名、图片文件名**里，所以第三步的 `find` 不能省。

## 容易漏的位置

这些地方不算正文，改正文时最容易忘：

- `LICENSE` 的版权人（公司名会被当成授权来源）
- `.claude-plugin/plugin.json` 与 `marketplace.json` 的 `author` / `homepage` / `repository` / `name`
- README 的 badge URL、外链、CI 徽章里的组织名
- `.gitignore`（里面写着内部路径，本身也是泄漏）
- 提交身份与提交信息：`git log --format='%an <%ae>%n%s'` 通读一遍（公司邮箱、工单号常在这里）
- `docs/` 里的示意图：SVG 是文本，grep 得到；PNG 或截图里的文字 grep 不到，必须**看图**
- 示例数据与 fixture：示例订单号、示例邮箱、示例 host
- 锁文件与依赖清单里的私有 registry 地址

## 反向检查：脱敏过度也是缺陷

改完通读一遍。如果替换掉的信息让某段话不再成立（"评审者说这个编号不能复用"被洗成"有人说这个不能复用"），就是删过头了。目标是**信息等价、身份无关**，不是把文本洗白。

## 与 SKILL §4（版权）的分工

脱敏只管"这是不是内部信息"，不管"这是不是别人的文字"。检查方法不同，不能互相替代：**脱敏是搜索，搬运检查是比对**。
