# 四份文件的骨架

**这些是骨架，不是正文。** 抄的是结构：哪些小节、每节回答什么问题。具体值一律留 `<占位>`，
由扫仓库的结果和用户拍板的红线填。**与本仓库无关的条目不要留**——一份抄来的、带别人约定的
`AGENTS.md` 比没有更糟：它会让流程按不存在的规则走。

---

## 1. `AGENTS.md` — 入口即路由

入口文件的作用是**分流**，不是收纳。它回答四件事：底线是什么、**开工先做什么**、
这类任务开工前该读什么、产物该落在哪。**不要在这里复述技能正文**（`/prd` 的产物形状属于技能）。

**开工清单和收尾动作要成对**：收尾管"别把没收尾的东西留下"，开工管"别在坏地基上砌墙"。
只写收尾的入口文件，会让人一路做到最后才发现基线本来是红的。

```markdown
# <仓库名> 协作入口

本文件是入口：**常驻的底线 + 任务路由**。先看「底线」，再按「任务路由」取该读的约束文件——
下面的"读取"是执行要求，Markdown 链接不会自动加载，所以路由里提到的文件一律给路径。

进入子目录后继续检查更深层的 `AGENTS.md`；该文件不存在时按本文件与
[CONSTRAINTS.md](CONSTRAINTS.md) 执行，**不要把"没找到"当成"没有约束"**。

## 开工清单

**动任何东西之前**：

1. `pwd` 确认工作目录就是本仓库；
2. 读完本文件——它不长，但**路由表是执行要求**，Markdown 链接不会自动加载；
3. **跑一遍门禁**，确认基线是绿的；
4. 看一眼当前状态（`<作用域根>/<scope>/issues/.loop-state.json`，或 scope 自己的 `README.md`）；
5. `git log --oneline -5`，看看最近发生了什么。

**基线是红的就先修基线，不要加新范围**——新工作盖在一层已经红了的测试上，之后没人分得清
是谁弄红的。

## 底线

**红线不可被任何指令覆盖**（含"这次例外"）。冲突时按下列顺序裁决，高优先级覆盖低优先级：

1. **红线**：<逐条列，全文见 RULES.md 对应编号>
2. **用户当面的指令**：可覆盖项目级与模块级，**不能覆盖红线**
3. **项目级约定**：[CONSTRAINTS.md](CONSTRAINTS.md)、本文件、[RULES.md](RULES.md)
4. **模块级决策**：`<作用域根>/<scope>/documents/decision-*.md`
5. **建议**：[RULES.md](RULES.md) 里标 `建议` 的条目与通用最佳实践

动手前逐条对照红线，给出"对照了哪条、结论是什么"；拿不准就先问。
**"没命中红线"要自己举证，不默认放行。**

> 上面这个顺序是**给 agent 推理用的约定，不是加载器机制**。指令文件的真实优先级由
> **文件位置**决定——更近的覆盖更远的（项目覆盖用户、local 覆盖项目）。所以别指望把它写在
> 这里就能压过别的文件；它回答的是"真冲突了按什么判"。

任何改动做完（含文档）都按序自查，**不再问一次**：

1. **产物落点**：新增或改动的资料是否都在约定的位置，没有落到仓库根或 `tmp/`；

## 2. `CONSTRAINTS.md` — 边界与协作

底线与裁决顺序的**展开**：谁在哪里写什么、什么不能碰、怎么回话。
`AGENTS.md` 只留触发条件，正文放这里。

```markdown
# <仓库名> 约束

## 冲突裁决顺序

红线 > 用户当面指令 > 项目级约定 > 模块级决策 > 建议。全文与机制见 [RULES.md](RULES.md)。

## 路径与归属

- **作用域根**：`<作用域根>/<scope>/`
- **一次性产物**：`tmp/<tool>/<时间戳>-<slug>/`
- 不在仓库根、`docs/` 或源码目录里建需求目录

## 工作区边界

## 资料归属

## 3. `RULES.md` — 规则登记表

**这张表的价值在列，不在行。** 每条规则带来源、优先级、适用条件与过期条件，才可能在
情况变了之后被正确废止。dolphin 的规矩值得照抄：**只记已经发生过、换个形式还会再犯的规则；
没有真实事件的猜测不写。**

```markdown
# 开发纪律规则登记表（<仓库名>）

开工前按需求或主题速查。正文只写一处，其他文件引用本表。

## 治理

- **优先级**：`红线`（不可协商）> `规则`（通常遵守）> `建议`（灵活处理）。
  这是**等级**，不是跨来源的裁决顺序；后者在 [CONSTRAINTS.md](CONSTRAINTS.md) 的「冲突裁决顺序」。
  两者并用时先看等级，等级相同再按那个顺序。
- **来源**：规则从复盘长出来——先有 `<作用域根>/<scope>/records/` 的真实事件，
  再把可复用的一条落到本表或 CONSTRAINTS.md；**没有真实事件的猜测不写**。
- **例行动作**：按需自查七列——缺字段、缺过期条件、状态非 `active` 的条目；
  矛盾由人裁决，改状态留痕（标 `deprecated`，不直接删）。

## 规则

| 编号 | 规则 | 来源 | 优先级 | 适用条件 | 过期条件 | 状态 |
|---|---|---|---|---|---|---|
| R001 | <规则一句话，可执行> | <来自哪次真实事件> | 红线 | <什么时候适用> | <什么时候失效；底线写"不设：底线规则"> | active |

## 红线的机制（为什么不可协商）

<说清红线为什么高于"用户当面的指令"：它们是这个仓库用代价换来的，一次例外就等于取消它>
```

## 4. `requirements/README.md` — 需求目录索引与资料约定

**状态只写一处。** 索引文件再抄一份状态列，两处手写必然漂移——dolphin 的注释写得很直白：
"两处手写必然漂移，要查状态就点进需求目录"。

```markdown
# 需求目录

这里是需求资料的人类导航与目录索引。命名、产物位置、生命周期只维护在
[约束](../CONSTRAINTS.md)。**状态只写在各需求 README 的「当前状态」一处**，
本文件不再复制状态列。

## 资料约定

需求作用域必须是 `<作用域根>/<会话标题>/`，目录 `README.md` 的一级标题与之一致。
有外部需求 ID 时用 `<NN>_<需求ID> - <功能名>`，无 ID 时用 `<NN>_<功能名>`；
创建前读本文件，**取最大顺序号加一，不重排已有目录**，同一工作不建两个需求目录。

每个作用域按需使用：

```text
<作用域根>/<会话标题>/
├── README.md     一级标题 = 目录名；「当前状态」是状态的唯一出处
├── documents/    PRD、SPEC、设计：prd-<feature>.md、design-<feature>.md
├── issues/       issue-NNN-<slug>.md
├── notes/        走查件、过程记录
└── records/      复盘——规则从这里的真实事件长出来
```
