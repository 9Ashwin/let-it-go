# 施工手册：正面做法与形态对比

本文件把素材里的**正面施工法**整理成可操作条目。十一组，每条注明对应讲次，并尽量给"改造前 → 改造后"的具体形态对比。
与 [diagnoses.md](diagnoses.md) 配合使用：诊断告诉你哪里坏了，这里告诉你该建成什么样。

**出处纪律**：条目默认出自这套方法论素材的对应讲次（讲次编号仅为溯源标签，见仓库 README 的 provenance 说明）。少数由本 skill 建设要求补充、**素材中未出现**的操作（如符号链接；「指针替代汇总」的写法形态来自 03、10 讲，但"不写会过期的数字"这一理由为本 skill 补充），显式标为「本 skill 补充（非素材主张）」并同时给出它对齐的素材原则；引用补充材料提供的机制词汇时同样注明出处。

## 1. 分层与渐进披露（Progressive Disclosure）— 05、11、14 讲

**原则**：入口文件只放核心规则和路径指引，细节放在专门文档里按需读取。信息在 agent 执行到哪一步时，才披露到哪一步。

**为什么**：两个硬限制——上下文窗口有上限、注意力分配不均匀。不加筛选地提供全部信息，重要指令会被挤到窗口边缘，随对话被截断或压缩；即使窗口够大，无关内容也会稀释注意力（一个常见的比喻：要把大模型当 ADHD 来照顾，首要任务是帮它保持注意力）。

**三层落法**：

- **入口层**（AGENTS.md / SKILL.md 元数据）：只写"是什么、在哪、什么时候读"。职责是路由，不是收录内容。
- **原则层**（如 `docs/constitution.md`）：红线 / 规则 / 建议，每条带 Rationale。
- **模块层 / 细节层**（如 `docs/decisions/adr-*.md`、`skills/*/`、`references/`）：按需加载。

**索引必须可解析**：入口里的每个引用要能被机械地检查——路径存在、编号能在登记表里找到、链接能点开。索引写错主题，agent 就会读错资料；资料更新了索引不更新，就会取到过时内容（14 讲）。

**改造前 → 改造后**

```
改造前：
AGENTS.md  ← 800 行，包含所有规则、所有模块的详细步骤、所有历史决策
             每次会话全文注入

改造后：
AGENTS.md（入口，只写：项目结构 + 模块清单 + 何时读哪份文档）
├── docs/constitution.md（原则层：红线/规则/建议 + Rationale）
├── docs/decisions/adr-003.md（模块层：这个模块为什么走中介层）
├── skills/<name>/SKILL.md（技能详情，只有被触发时才读）
└── references/<name>/（范例与参考实现，只有需要时才读）
```

## 2. 前馈 ↔ 反馈的配比 — 01、05、12 讲

**原则**：需要新增一条控制时，先写它的**检查形式**，再考虑过程规则。前馈提高"做对的概率"，反馈提供"做对的证据"；两者缺一不可，但默认动作应当是反馈优先。

**什么时候该加规则、什么时候必须改成检查**：

| 你想表达的东西 | 正确形态 | 理由（讲次） |
|---|---|---|
| 结果必须满足某个可观察条件 | 检查项 | 检查在反馈环节一定会被执行（12 讲） |
| 目标、取舍、风格、领域知识 | 前馈规则 | 无法机械判定，需要理解（12 讲） |
| 确定性的重复计算（日期、间隔、计数、格式） | 脚本/工具 | 用模型算既贵又不稳（02、05 讲） |
| 语义判断（语气、通顺、风险是否充分） | 推断型检查 | 硬编码成规则写不出来也维护不了（02 讲） |

**改写模板**：把 `必须 X` 改写成 `检查 X 是否成立`。必要时给判定口径，否则检查项本身会变成新的模糊需求。

- `亮点必须带数据` → `检查亮点部分是否包含数据（数字或百分比）；没有则补上或标注"无数据"`。
- `语气要客观` → `检查是否出现套话（如"扎实推进"）；出现则改写为具体结果`。
- `覆盖率不低于 90%` → `运行 coverage 脚本，检查报告中 total 是否 ≥ 90%，输出 PASS/FAIL`。

改写不出来的规则，往往是"什么叫有数据"这类连你自己都没想清楚的问题。处置办法：让模型扮演苛刻的面试官连续追问，直到验收口径被澄清，再落成检查项。

**成本分界（05 讲）**：高频、确定的逻辑交给代码；低频、模糊的判断交给模型。代码处理六到七成可形式化的检查，模型覆盖三到四成需要语义理解的部分——这是成本最优解，不是风格偏好。用模型做"检查数字是否在范围内"，等于用超级计算机算小学数学题。

**改造前 → 改造后**

```
改造前（前馈膨胀）：
## 要求
- 亮点必须有数据
- 语气要客观
- 阻塞项必须写责任人
- 不要用套话

改造后（反馈优先）：
## 完成检查（交付前逐条执行）
1. 检查亮点是否至少 2 个，且每条含数据（数字/百分比）
2. 检查是否出现套话词（空话、重复、模板化表达），出现则改写
3. 检查阻塞项是否写责任人；无责任人则标注"待指派"
→ 其中第 1、3 项能机械判定，落成 check_report.py，输出 PASS/FAIL
```

## 3. 规则的治理（Instruction File Governance）— 08、11 讲

**原则**：规则要能被裁决、被过期、被清理。治理的重点不是一次性建结构，而是让维护**持续发生**。

**规则登记表格式**（11 讲）：

```
编号: RULE-001
内容: 一句话描述
来源: 为什么加这条规则
优先级: 硬约束 / 规则 / 建议
适用条件: 什么时候需要这条规则
过期条件: 什么情况下可以删除
状态: active | superseded | deprecated
```

**六条硬纪律**：

1. **优先级分级**：至少红线 / 规则 / 建议三档，与 08 讲的五级裁决顺序对齐（红线 > 用户当面指令 > 项目级 > 模块级 ADR > 最佳实践）。优先级是矛盾检测与清理的共同依据。
2. **过期条件**：无过期条件的规则永远不会被清理，等于永久债务。
3. **状态位**：`active` / `superseded` / `deprecated`。状态让"这条还算不算数"变成可查询的事实，而不是靠记忆。
4. **删除留痕**：被清理的规则标 `deprecated`（或 `superseded`）并保留原文与理由，不要直接消失。以后审计时还能看到曾经有过这条规则、为什么被删。
5. **编号是身份，不重排**：编号一旦分配就固定，删除或废弃后不复用、不重排。重排会让所有既有引用腐烂——文档里引用的编号、评审意见里的编号、脚本里的白名单全会指向错误对象。**本 skill 纪律**（延伸自 11:103 的留痕与可审计要求：删除要留痕，被清理的规则标记而不消失，审计时还能看到曾经有过它以及为什么被删）。
6. **例行清理机制**：把矛盾检测与清理做成固定动作——定时任务，或每次会话开始时检查一遍。不要"靠人想起来"。

**矛盾检测的做法**（11 讲）：逐对检查规则的**适用条件是否有重叠**，只有重叠的规则才可能矛盾；对重叠规则判断行为是否互斥、是否可能被同时触发；输出冲突报告，按优先级给裁决建议（优先级高的胜出；同级时更接近当前现实的胜出；裁决不了的标"待人工"）。同级的隐式矛盾最危险——agent 每次会随机选一条，显式化之后才能处理。

**改造前 → 改造后**

```
改造前：
## 关于接口规范
一般来说接口要按 REST 风格来写。但是历史遗留的 A 模块用的是 XML 接口，
所以 A 模块可以例外。另外如果第三方要求，也可以例外。除非……
（规则散落在散文里，没有编号、优先级、过期条件）

改造后：
docs/rules.md
编号: RULE-001 | 内容: 新接口按 REST 风格 | 优先级: 规则 | 适用条件: 新建接口
过期条件: 全部存量 XML 接口下线后 | 状态: active
编号: RULE-002 | 内容: 遗留模块接口保留 XML | 优先级: 模块级约定 | 适用条件: 仅该遗留模块
来源: 兼容已停产的第三方系统 | 过期条件: 该第三方系统下线 | 状态: active
（RULE-001 与 RULE-002 适用条件重叠，但 RULE-001 已把遗留模块排除，无矛盾；
  若两者行为互斥，则由优先级裁决，并在冲突报告里留档）
```

## 4. Skill 的写法 — 04、20 讲

**原则**：技能是把操控循环打包成可重复使用的单元，判据是**可预测**——每次跑出类似的过程，而不是相同的输出。

**四环节完整性**：SKILL.md 正文用自然语言写清 Guides / Action / Sensors / Steering。四个环节缺失比臃肿更常见（20 讲）。

**description 的写法（唯一常驻的竞争位）**：

- 重点写**什么时候用**，而不是"这个技能能干什么"。
- 写出**"不要用在哪儿"**，尤其是可能存在竞争技能时。

```
改造前：description: 帮助用户整理发布说明。
改造后：description: 当用户要发版本、整理更新日志、或说"给这次上线写个说明"时使用；
        不要用于面向最终用户的产品公告。
```

```
两个技能撞车时：
改造前：技能一"帮助处理数据" / 技能二"帮助整理文档"
改造后：技能一"当用户要回答数据问题、得出结论并给出依据时使用；不做文件格式转换。"
        技能二"当用户要把已有内容转成另一种文件格式时使用；不负责分析与结论。"
```

**模型调用 vs 用户调用**：带 description → 模型可自行触发；摘掉 description → 只有用户点名或别的技能明确指定才触发。摘掉的收益是消除模糊性，代价是认知负载压到人身上，且别的技能也叫不动它。

**恰当的自由度**（20 讲，按四环节里有多少交给模型）：

| 档位 | 定死什么 | 交给模型什么 | 适用 |
|---|---|---|---|
| 低 | 四环节全定死；Guides 逐字命令、Sensors 是确定信号、Steering 失败即停 | 只执行 Action | 做错了不可逆、必须每次一致 |
| 中 | Guides 和 Sensors | Action 里的选择 | 形状固定、内容自由（多数场景） |
| 高 | 只给方向与标准 | Action 怎么走、Steering 怎么转 | 探索性、需要适配现场语境 |

选档的判据：**这一步做错了能不能倒回来**。

**体积控制与拆分**：

- 先看四环节缺不缺，再看是哪一环膨胀：前馈膨胀 → 前馈痴迷（12 讲）；反馈膨胀 → 反馈过载（13 讲）。
- Action 膨胀通常是逐字命令过多；把反复出现的机械操作**收敛成一个脚本调用**。这不只是长度问题，也是自由度问题。
- Steering 膨胀通常是异常分支铺成决策树；只留几条关键转向——什么情况停下、什么情况重试、什么情况升级给人，剩下交给模型判断。
- 结构没问题后再看数字：正文控制在约 500 行 / 5000 token 以内，这是实测拐点。
- 超过拐点才拆分，主要依据是**能否提取一个独立的触发器**；拆出来的技能必须自己有完整四环节。只有 Action 的是被挪走的一段说明；只有反馈的，应是分级反馈里的一步。

**改造前 → 改造后**

```
改造前（Action 逐字化 + 无反馈）：
**Action**：先运行 python gen.py --format png --width 1024 --seed 42，
再运行 python upload.py --bucket xxx，再运行 python notify.py …

改造后（收敛脚本 + 补反馈）：
**Guides**：分镜提示词已确认，需要产出配图。
**Action**：调用 `render_and_upload.sh`（内部封装渲染、上传、通知三步）。
**Sensors**：检查产物存在且格式为 png，且上传返回的引用可访问（脚本退出码非 0
            即失败，不解析对话内容）。
**Steering**：渲染失败重试 1 次；上传连续失败则升级给人，不自行改写产物。
```

## 5. 状态与跨会话 — 02、04、15、16、17 讲

**原则**：状态子系统是内外两层的桥梁，也是唯一真源。设计状态时要回答三件事：谁写、写什么、跨不跨会话。

**状态分区**：按生命周期分开。

- **临时状态**（草稿纸）：执行数据、中间产物、工具原始返回、未验证结论。随任务消亡。
- **持久状态**：进度、决策、知识、用户偏好。只有经过核验/整合的内容才进得来。
- **唯一主人**：进度由外层循环负责读写；内层只交回交付物，没有直写持久状态的通道（17 讲）。

**指针替代汇总**（形态来自 03、10 讲的"进度怎么查"表：03:168–175、10:63–73；**"常驻文档里不写会过期的数字"这一理由为本 skill 补充，非素材主张**，对齐 17 讲"状态唯一主人"与 05 讲"进度从文件读取而不是靠人记住"）：常驻文档里不要写会过期的数字（如"当前 500 个单词""共 12 条规则"），写"去哪儿查"。

```
改造前：## 当前进度
       已掌握 320 个单词，剩余 180 个。（数字每天都会过期）
改造后：## 进度怎么查
       | 问什么 | 从哪看 |
       | 掌握情况 | state/vocab/progress.json 的 stats.mastery_rate |
```

**知识清点三类与归位（16 讲）**：任务收尾时，交付结果之前先清点本轮知识——

1. **用户统筹**：用户表达的偏好/优先级。记录内容 + 适用场景 + 来源（用户）。
2. **发现**：执行中对照出来的事实。记录内容 + 来源（执行）+ 时间。
3. **决策**：做出或接受的裁决。记录结论 + 理由 + 适用范围 + 来源（用户/模型）。

归位由**外层循环**做，因为只有它知道知识该住在哪（决策进 ADR 还是规则文件、领域知识对应哪份文档、偏好归哪个文件）。

**checkpoint 必留四项（15 讲）**：每转一圈（Check 环节）压缩存档，其中以下四项**原样**保留，不能只留摘要：

- **进度**：做到哪一步、哪些阶段已完成。
- **关键决策及理由**：理由丢了，后续会话要么推翻既定决策，要么把犯过的错再犯一遍。
- **验证记录**：什么通过、什么失败、失败原因；决定下一步能不能信任已有结果。
- **未决事项**：接下来要做什么、还有哪些悬而未决。

过程性内容（讨论过程、试错中间步骤、检索到的资料细节、确认无关的旧信息）压成摘要即可。

**改造前 → 改造后**

```
改造前（单文件、混装、谁都能写）：
state/all.json
  { "current_week": 3,
    "last_session_correct_rate": 0.72,      ← 单次执行数据
    "mastery_rate": 0.85,
    "note": "用户说这个词已经会了",           ← 未归位的用户统筹
    "_debug_tool_raw": [...] }               ← 工具原始返回

改造后：
state/<module>/progress.json   ← 只放跨会话的原始指标（掌握率、到期卡片数）
state/<module>/plan.json       ← 外层下发的计划参数（current_week、phase）
scratch/<session-id>/          ← 草稿纸：本次执行数据、工具原始返回，任务结束销毁
docs/decisions/ + docs/rules.md ← 知识归位后的去处（决策带理由与适用范围）
checkpoints/<cycle>.md         ← 进度 / 关键决策及理由 / 验证记录 / 未决事项
```

## 6. 环境（Environment Locking）— 02、05、18 讲

**原则**：反馈信号只在一致的环境中才有意义。环境的核心是可复现性。

**四类要锁的东西与对应做法**：

| 类别 | 做法 |
|---|---|
| 运行时 | `init.sh` 从确定状态开始；用 `.nvmrc` / 语言版本文件锁运行时 |
| 依赖 | lockfile 锁精确版本（`requirements.txt`、`pyproject.toml`、`package-lock.json` 等） |
| 第三方 skill | 局部化到项目 `skills/third-party/`，pin 到 tag 或 commit，与项目一起进版本控制；只加载项目内与内建的 skill |
| 外部服务 / MCP | 经 MCP 服务器做间接层；MCP 服务器同样局部化、固定版本 |

**初始化入口**：`init.sh` 固定文件夹结构、配置文件与初始状态。可以顺带做一致性检查：跑初始化时校验 `skills/third-party/` 下每个 skill 的实际内容与锁定版本是否一致，不一致就报错停下（拿不准时停下来、不带着不确定性继续——这一取向常被称为"失败关闭"（fail closed），属补充机制词汇）。

**镜像用符号链接而非副本**（本 skill 补充，非素材主张；对齐 18 讲"同一份东西只固定一次"的思路）：当同一份资料需要在多处被引用时（例如多个技能共用一份参考文档或脚本目录），用符号链接指向唯一副本，而不是复制多份。副本会各自漂移，链接不会——链接天然维护"同一事实只有一份"。

**分发**：完成局部化后，把整个 harness 打成容器镜像，换机器、换个人跑起来就是相同环境。这一步放在最后，因为它打包的正是前面已经固定下来的东西。

**改造前 → 改造后**

```
改造前：
README 里写"先 pip install fsrs，再 pip install requests，注意版本别装错"
skills 从全局目录加载（~/.<agent>/skills/ 里装了什么就是什么）
AGENTS.md 里的 API 调用直接写外部地址

改造后：
init.sh                     ← 一条入口，装依赖 + 建目录 + 校验版本
requirements.txt            ← 精确版本
skills/third-party/skill-a/ ← pin 到 v1.2.0，随仓库提交
AGENTS.md 规矩：第三方 skill 必须装在项目内并锁版本；只认项目内与内建的 skill
MCP 服务器局部化，固定版本
（可选，最后一步）Dockerfile ← 把固定好的环境整体打包
```

## 7. 反馈分级（Grade Feedback）— 10、13 讲

**原则**：不同严重程度的信号用不同的呈现方式，让 agent 一眼看出先修哪个。分级的实质是**责任分界**，不是严重程度的修辞。

**第一原则**：成功静默，失败才输出。全部通过时不输出或只输出一句"全部通过"。

**三级（三层已经足够）**：

| 级别 | 定义 | 呈现方式 | 责任归属 |
|---|---|---|---|
| 阻塞级 Blocking | 不修就不能交付（编译失败、测试挂掉、数据引错） | 完整信息，最醒目 | 模型必须完成 |
| 警告级 Warning | 应该修但不阻塞（字数、覆盖率、术语检查） | 摘要输出，给出评估值 | 模型评估 → 人决定是否继续完善 |
| 信息级 Info | 不影响结果（成功消息、风格偏好、普通日志） | 默认静默，需要时才看 | 通常可直接转成前馈 |

**为什么不要分更多级**：agent 还要花力气区分级别，等于把反馈过载换个形式再来一次。判据是责任：哪些是模型必须完成的，哪些可由人判断是否值得继续花力气。

**改造前 → 改造后**

```
改造前：
运行 npm test && npm run lint && npm run typecheck，把三份完整输出都贴给 agent

改造后（AGENTS.md / 检查脚本的呈现约定）：
级别            内容                                    输出
阻塞级  pytest/typecheck 失败                          完整失败信息 + 文件:行 + 断言
警告级  lint 违规                                      仅计数 + 前 5 条摘要
信息级  通过项、跳过项、耗时                            静默（需要时加 --verbose）

改造后（验收清单同步分级）：
要求（按优先级分组）：
- 阻塞级：数据准确；三个核心卖点齐全；结尾有行动号召
- 警告级：字数 800–1000（不达标时只报告当前字数，不盲目扩写）
- 信息级：语气活泼（写得顺手就做，不为此返工）
```

## 8. 范例优先于约定（Pattern Baseline）— 19 讲

**原则**：当"仓库里既有的样例"与"你写下的约定"冲突时，范例通常权重更高——你的约定是几条，仓库里的旧模式是几十上百个示范。所以要处理样例本身，而不是只加强指令。

**四步（顺序有依赖，缺一不可）**：

1. **正向范例**：给新写法的参考实现，放固定位置（如 `references/`），在入口文件里指路。
   - 用**独立**的参考文件，不要指向项目里会被改动的实际代码——被改动的代码就失去了参考意义。
   - 写不出范例时，找一个独立的外部参照（已改好的仓库、示范工程）。
2. **确立架构约束**：把约定变成**会失败的自动化检查**（自定义 linter、架构测试），让"照旧样例写"失败。
   - 原则：**强制不变量，不微观管理实现**。可以要求"业务逻辑不得出现在 controller"，不规定 service 方法怎么切——否则会束缚 agent 解决问题的能力。
3. **建立基线**：先把现存违规全部记入基线文件，之后只许减少不许增加；有新增违规立即停下修复。
   - 好处：避免一次性重构存量带来的改坏风险与 token 浪费。
4. **持续清理**：任何一次改动只要碰到存量代码，就在这次改动里按新模式重写。约束指出不合规，范例指出该怎么改，清理不需要额外努力。

**为什么要"范例 + 约束"两条腿**：范例告诉 agent 该照着谁写（给方向）；约束让照着旧的写就失败（给边界）。少了范例，约束拦得住越界却给不出方向——agent 无路可走时会就近抄一个；少了约束，方向推不过仓库里的多数派。

**约束的成长方式**：不必一次设计完，用知识固化一轮轮长。每次 agent 犯一个新的架构错误，或评审里出现一条新的重复意见，就问一句"这条能不能变成一条检查"。能机械判定的补进约束，需要人判断的补进约定或范例。

**改造前 → 改造后**

```
改造前：
AGENTS.md 写"新的业务逻辑放在 service 层，controller 只做参数校验和转发"，
仓库里 controller 直接调 mapper 的有几十处，测试大量用 Mock 分层。
（约定是前馈，没有反馈；agent 继续按旧样例写）

改造后：
references/testing/api/           ← 正向范例：API 层的参考测试与参考 service
architecture-tests/               ← 架构约束（会失败的检查）
  controller_should_not_access_db_directly()
  API_test_should_not_use_mock()
baseline/architecture-baseline.txt ← 现存违规冻结，只许减少
AGENTS.md：改到存量代码时，在本轮内按 references/ 的新模式重写；
           架构检查出现新增违规时，停止当前工作先修复违规
```

## 9. 仓库即规范（Repository as Spec）— 03、05、09 讲

**原则**：仓库是 Agent 系统的**唯一事实来源（Single Source of Truth）**。Agent 需要的一切信息都以文件形式放在仓库里；不在仓库里的，对 Agent 来说就等于不存在（05:17–19、03:42）。

**为什么**：

- **根治信息不一致**：使用 AI 最常见的问题是同一件事今天在对话框里说一遍、明天再说一遍，今天多提一句项目背景、明天漏说一条技术约束；Agent 每次都按当前对话上下文执行，输出自然忽好忽坏（05:17）。信息固化进仓库后，换一个人、换一台机器、换一个 Agent 系统，只要仓库是同一个，行为就是一致的（05:19）。
- **留下可追溯的变更轨迹**：Agent 每次操作的证据都留在仓库里——改了什么文件、为什么改、结果如何；靠的是版本历史，而不是人的回忆或聊天记录。这也是 Git 仓库是 Harness 最佳载体的原因：版本控制、协作、回滚、分支实验都来自仓库本身（05:21）。
- **状态子系统通常也以文件形式保存在仓库中**：进度、决策、质量指标与代码一起版本化；进度不是靠人记住"背到第几周了"，而是每次从文件里读取（05:25）。
- **仓库以 Agent 优先（Agent-first）设计**，不考虑人的阅读习惯：仓库结构、目录布局、文档体系、配置文件与验证脚本都围绕 Agent 的读取与执行习惯（例如"从 plans/vocab/week-NN.md 读取本周词汇"），服务于导航效率而不是人的完整阅读体验（05:27）。

**落法**：

- 需要的信息一律落盘，不要留在对话里；MCP 服务器传回的数据可以不入库，但 MCP 服务器的配置仍必须保存在仓库内（03:42）。
- 仓库即规范不等于"汇聚了就一定同步"：汇聚到仓库的知识可能来自不同来源，必须配套更新机制，否则会退化成信息散落（09:5；见 diagnoses §3）。
- 仓库同时是唯一事实来源与状态载体，所以"同一事实只有一份"这条纪律在这里是默认成立的前提（03:40–42）。

**改造前 → 改造后**

```
改造前：
项目背景、约束、进度散在聊天记录和某个人脑子里；
新会话要重新交代一遍，每次交代的详略都不同。

改造后：
AGENTS.md             ← 结构、约定、完成条件（入口）
plans/week-02.md      ← 本周要用的词表（学到第 2 周才读）
state/*/progress.json ← 进度按文件读写
全部进 git            ← 变更可追溯、可回滚、可分支实验
```

## 10. 最小干预（Least Intervention）— 05 讲

**原则**：尽可能通过反馈（Sensor）去纠正 Agent 的行为，而不是主要依靠人为干预。把重复性的、可预测的检查自动化，让 Agent 自己发现问题、自己修正（05:71）。

**为什么**：

- **这是操控循环的内在要求**：外层 PDCA 管流程与进度，需要人参与决策（下一步做什么、计划要不要调整）；内层操控循环的设计目标就是让 Agent 自己完成"检查 → 调整 → 再检查"的闭环，不需要每轮都向外层请示。如果 Agent 做完一步就等人指出错误，Steering 环节就失去了存在的意义（05:73）。
- **人的认知负担是现实约束**：每轮人工检查看似只是"看一眼"，但上下文切换的成本远高于那一两分钟的阅读时间；次数多了，大部分人都会放弃参与，盲目接受 AI 给出的结果——然后在几小时后抱怨 Agent 给不出想要的结果（05:75）。
- **坚持反馈的人会成为最慢的瓶颈**：即使一直坚持为 Agent 提供反馈，人也只是 Agent 系统里最慢的那一环；好的驾驭机制不追求消除人类输入，而是把人类输入引导到最重要的地方（05:77）。

**落法**：

- 把"等人通读产出并指出错误"改成"把可预测的检查写成脚本或检查项，让 Agent 在反馈环节自己走一遍"（05:71）。
- 人的位置是**裁决与升级**，不是**逐轮扫描**：目标与优先级、例外与冲突裁决交给人；重复的一致性检查交给自动化（05:77）。
- 与分级反馈配套（见 §7）：不是取消人的判断，而是让人的判断只花在值得的地方。

**改造前 → 改造后**

```
改造前：
Agent 交付 → 人通读全文 → 人逐条指出问题 → Agent 改 → 人再通读
（人充当 Sensor，而且是最慢的那一个）

改造后：
Agent 交付 → 自动检查（脚本/检查项，成功静默、失败分级）→ Agent 自纠
人只在两类时刻介入：需要裁决的冲突、需要改目标或优先级的决策
```

## 11. 知识固化（Knowledge Solidification）— 06 讲

**原则**：把存在于对话中的、临时性的知识逐步写入文件，变成持久的、可复用的规则和工具（06:9）。构造 Harness 时不必纯手工：在对话中纠正它、补充它、引导它，经过几轮试错和迭代得到满意结果后，按 Harness 架构把知识逐步写入指令、状态、工具和环境四个子系统（06:9–11）。

**为什么**：

- **知道与做到之间的门槛被填平了**：AI 时代之前，知道计算型控制更可靠但写工具需要编程能力、知道前馈反馈更高效但写指令要反复调试格式与措辞；现在只要在概念上理解双层循环、了解四子系统、知晓最佳实践，就能通过知识固化指导大模型完成 Harness 构造（06:15–17）。
- **固化不只发生在构造阶段**：后续持续改进同样关键。发现 Agent 反复犯同一个错误，在对话里纠正、几轮试错后找到有效做法，把这条规则写进 AGENTS.md 就是一次改进中的固化；没有固化，改进永远是临时补丁，有了固化，每一轮改进都在让 Harness 更完善（06:329–331）。
- **Know-how 可以被封装进上下文**：为具体任务提供操作说明与关键经验是前馈控制；执行后按结果检查与反馈，未达到要求就依据前馈信息调整方向、重新执行（直播回放:129–137）。

**落法**：

- 对话只当"临时工作区"：在对话里把方案谈对，然后立刻固化到对应子系统（指令/状态/工具/环境），不要让它停留在上下文里（06:9–11）。
- 持续固化会带来不一致：从对话里一轮轮固化时，职责边界可能跑偏（例如每个技能都塞进一份计划调整逻辑，技能文件变得冗长、执行时失去注意力）。此时用最佳实践回头对齐——双层模型下计划归外层、技能只做执行与记录——这一轮修正就是重构（06:256–323）。
- 每轮改进的收尾动作：把本轮确认有效的做法写进文件，并说明它落在哪个子系统（06:331）。

**改造前 → 改造后**

```
改造前：
对话里已确认"计划调整放 AGENTS.md，技能只负责执行和记录"。
下一轮换个技能，同样的逻辑又被写进技能里——知识只在对话里生效。

改造后：
对话里确认做法 → 立即写进 AGENTS.md（外层职责）→ 技能 Overview 标注
"本技能仅负责执行，不负责任何计划调整决策" → 提交 git
下次会话从文件读到，不再依赖"上次说过"
```
