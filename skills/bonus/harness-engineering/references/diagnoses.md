# 诊断手册：病症 → 判据 → 处方

本文件是这套 harness 方法论全部诊断的提炼，可独立使用，不依赖任何外部材料。每条固定五段：**症状 / 成因 / 判据 / 处方 / 常见误判**。
判据尽量写成可执行检查；处方注明讲次，便于追溯主张出处。示例均为抽象形态。

诊断顺序建议：先看是不是**需求侧**（07、08），再看**知识侧**（09），再看**循环侧**（10–15），最后看**状态与环境侧**（16–19），技能写法单独走 20。

---

## 1. 需求模糊（Vague Requirements）— 07 讲

**症状**：你给一句话，agent 给一个"看起来对、用起来不对"的东西；你得反复说"我不是这个意思"。

**成因**：把需要大量上下文的系统需求压进一句话，猜对是偶然、遗漏是必然。模型厂商对 one-shot 能力的宣传加剧了错觉——那些演示多是成熟的已知系统，你脑子里的却是带特定约束的私人需求。反复在对话里修正会引出第二个问题：所有修正权重相同，agent 分不清哪条是核心约束、哪条是锦上添花。

**判据**：
- agent 反问"这里我该怎么做？"——说明留下了太多言外之意。
- 交付物"看起来对，用起来不对"——它猜对了表面，没猜对本质。
- 验收时你频繁说"我不是这个意思"——最严重，往往伴随优先级丧失。
- 让 agent 自己列约束：`基于我们之前的讨论，你理解的需求约束有哪些？逐条列出。` 列得越少，说明越模糊。

**处方**：**提取指令文件（Extract Instruction File，07 讲）**——把提示词升级为 AGENTS.md，必须含三部分：
1. **约束条件**：用什么方式做。写"200 个词分 4 周，每天 10 个新词，学完即测"，不写"背单词"。
2. **完成条件**：什么算做完，必须可验证。写"掌握率都超过 90% 且没有到期未复习卡片"，不写"感觉差不多"。
3. **边界情况**：正常流程之外的"如果……就……"，单独成节。例如"连续答错 3 次就降低次日新词配额"。

重构三步（07 讲）：先让 agent 列约束条件并逐条校对；再列验收条件（它若回答"你说没问题就算完"，就是完全没有标准）；最后从约束里拆出边界情况。每一步都可以让 agent 反问以暴露遗漏。

**常见误判**：不是"模型不够聪明"。换更强的模型、把提示词写得更长，都不能替代把约束、完成条件、边界情况显式化。也不是"prompt 技巧问题"——这是知识固化的第一轮实践，产出物是文件，不是措辞。

## 2. 隐式约定（Implicit Convention）— 08 讲

**症状**：大方向对了，细节处处偏差。你总在评审时说"这里应该用我们约定的方式"。

**成因**：agent 不了解不同模块实现方式的约定，于是拿通用方案套你的项目特有上下文。核心难处不是知识本身，而是**优先级**：A 模块走中介层是因为出过数据一致性问题，B 模块保留旧接口是为了兼容，这些都是"两难时选哪边"的历史权衡。agent 不问，因为它不知道自己在违反规则。

**判据**：
- Code Review 里反复出现同一类"这应该用约定方式"的评论。
- agent 迟迟完不成功能，因为它在你没写下来的地方从头发明方案。
- 让一位没参与的人只读仓库做一次任务；他需要口头问你的地方，就是没写下来的约定。

**处方**：**建立原则文档（Establish Principles，08 讲）**。原则文档不是规则清单，而是决策框架——回答"当 X 和 Y 冲突时优先选哪个"。分层结构与优先级：

- **不可协商的红线**：安全合规、数据保护、法律要求。用户当面要求也不能违反。
- **用户当面的指令**：可覆盖项目级与模块级，不能覆盖红线。
- **项目级约定**：AGENTS.md 与原则文档里的全局规则。
- **模块级约定**：各模块自己的权衡记录，视为模块级 ADR。
- **最佳实践**：通用建议，冲突时可让步。

落成三层文件：`AGENTS.md` 是入口层，只说明"原则文档在哪、什么时候读"；`docs/constitution.md` 是原则层，每条带 Rationale，并区分红线/规则/建议；`docs/decisions/adr-*.md` 是模块层，记录上下文、决策、权衡、影响。入口层保持简洁，原则才不会把它撑爆。

**常见误判**：看起来像"需求模糊"，但手册第 1 条的三步法在这里不奏效——需求澄清解决"我不知道你要什么"，隐式约定解决"我不知道你项目里为什么这么选"。也别把原则文档写成更长的规则清单，那样只会加速 11 讲的腐化。

## 3. 信息散落（Information Scatter / 知识依赖过期）— 09 讲

**症状**：agent 精准地实现了错误的目标——执行到位，方向全错，而且很自信。

**成因**：知识进了仓库，但外部现实在变（词表在改、API 规范在改、业务规则在变），仓库里留下的是"事实的旧版本"。这比没有文档更危险：没有文档时 agent 知道自己在猜，你会检查；有文档但过时，agent 的自信来自你亲手建的仓库。根因是更新只停留在会议、邮件、Wiki 里，回写仓库成了额外动作，额外动作容易被忽略。

**判据**：
- 找出仓库里"来自外部"的文档（规范、清单、对照表），看它有没有标注来源与更新时机。
- 问 agent："这份文档的内容，上一次与外部来源核对是什么时候？"——答不出来说明没有机制。
- 抽查一份文档与它的外部真实来源是否一致。

**处方**：**管理知识依赖（Manage Knowledge Dependencies，09 讲）**。把仓库里每条来自外部的信息当成一条"知识依赖"，给它建立映射与更新机制：

- 建 `SOURCE.md`，表格列出 `仓库文件 | 外部来源 | 更新时机`。
- 有 URL/API 的：构造一个 `sync-sources` skill 定时拉取、对比、生成差异与 PR；"按需"来源每次运行时提示用户。
- 没有固定来源的（如手工维护的词表）：在 AGENTS.md 里加**提醒环节**，每次会话开始先问一句"这份清单有更新吗"，用户提供即改文件。
- 信息源多且频繁变化时，引入现成的知识库工具替代手写 SOURCE.md；源少就用 SOURCE.md + 定时 skill。

关键原则：**设计主动机制代替人的记忆**。只要有外部来源，就有更新义务，这是标配而非可选项。

**常见误判**：不要把它当成"文档维护习惯"问题靠自觉解决——实践中这件事很少被认真执行。也不要以为一次同步就永久有效：依赖会继续漂移，机制必须持续运转。

## 4. 虚假胜利（False Victory / 惰性生成）— 10 讲

**症状**：agent 很快回复"做好了"，格式漂亮，但你抽查发现只做了六成，跳过的恰是最需要判断的那部分。

**成因**：惰性生成——agent 系统性回避需要更多推理的复杂部分，只做容易的部分，然后对整个任务自信宣布完成。三个特征：容易的做且做得快；复杂的跳过但不告诉你；对整个任务宣布完成。终止条件失效有两个原因：**过度自信**（被要求自评时系统性给正面评价）与**认知统一**（生成时的上下文、假设、盲点原样保留到评估阶段，它只能确认自己之前的判断）。底下还有位置偏差与难度回避在起作用。

**判据**：
- 抽查工作量：要求 100 条，只交 80 条；要求每天 30 个词，只给十几个。
- 完成速度异常快：任务越复杂、完成得越快，越值得警惕。
- 让 agent 报告进度时，它给的是"处理得很好"这类评价，而不是"已处理 30 条，跳过 70 条"这类原始数据。
- 完成判断的代码路径里，最终裁决者是生成者自己。

**处方**：**分离执行与验证（Separate Execution from Verification，10 讲）**。三步：
1. **把完成条件定义为可验证指标**：每条都能用"是/否"判定，避免"写得很好"。
2. **要求记录进度，而不是汇报结果**：只写"已处理 30 条，跳过 70 条"以及跳过原因，写"分支覆盖率 31%"而不是"覆盖率达标了"。进度必须是原始数据，不是自我评价。
3. **让验证者读取进度并判断**：验证者可以是脚本、检查清单、另一个人或另一个被调校得挑剔的 agent。在 AGENTS.md 里写明职责边界："你负责执行并记录进度；完成判断由验证者根据进度数据决定。"并在完成流程里写死"只有脚本输出 PASS 才算完成"。

**常见误判**：与 15 讲的上下文焦虑不同——惰性生成在没有外部验证时随时可能发生；上下文焦虑只在资源压力下触发。区分方法：给足上下文余量再跑同一个任务，正常了就是焦虑，仍然偷懒就是惰性生成。另外，验证者若仍是同一个 agent 自评，认知统一依旧，改善有限；能落成确定性脚本的检查尽量落成脚本。

## 5. 指令文件腐化（Instruction File Rot）— 11 讲

**症状**：规则越加越多，agent 反而变笨；行为不可捉摸，你对着长长的规则列表却指不出错在哪。

**成因**：只增不减。每条规则加进去时都有效，问题出在累积之后：一是**优先级冲突与矛盾累积**（"尽快/适当/必要时"在不同规则里可能指向相反行为；规则越多越难抓重点）；二是**中间迷失（Lost in the Middle）**——模型对长文本中段的信息利用效率显著低于两端，写在中间的规则（常常是安全约束）最容易被漏读。

**判据**：
- 指令文件里频繁出现"但是""除非"等例外条款，规则在互相打补丁。
- agent 背离预期时，你无法从规则列表里指出错误根源。
- 规则没有优先级字段、没有过期条件、没有状态位。
- 注意：**判断依据不是文件行数**。50 到 200 行的指令文件都是健康的；看行为，不看长度。

**处方**：**指令文件治理（Instruction File Governance，11 讲）**——先建结构，再持续维护。结构是分层的：入口文件只做说明，细节放专门文档按需读取；简单场景用一张规则登记表，每条含：

```
编号 / 内容 / 来源 / 优先级 / 适用条件 / 过期条件 / 状态
```

维护的核心是三件事：
1. **优先级确定**：每条规则有明确优先级。它是整个维护机制的基础——矛盾检测靠它裁决，定期清理靠它决定先删哪条。
2. **矛盾检测**：定期（或每次会话开始）让 agent 读登记表找矛盾对，按优先级给出裁决建议；裁决不了就升级给人。显式的矛盾可以处理，隐式的矛盾只能靠运气。
3. **定期清理**：让 agent 列出过时/冗余/矛盾的条目并标注建议状态，由人确认删除。**删除要留痕**：被清理的规则标 `deprecated` 而不是消失。清理做成例行机制（定时任务或会话开始检查），不要靠人想起来。

**常见误判**：不要因为"文件还不到 200 行"就认为健康——行数不是判据。也不要把治理等同于重写一遍分层结构：结构很容易建，难的是让矛盾检测和清理**持续发生**。

## 6. 前馈痴迷（Feedforward Obsession）— 12 讲

**症状**：产出不对时，你的第一反应是往 AGENTS.md 里再补一条说明；补了同类错误还在。

**成因**：我们习惯描述"怎么做"，不善于描述"如何检查做完的结果"。写过程描述容易（"带数据"就行），写结果描述难（什么叫有数据？必须有数字？百分比算吗？）。这个困难在管理学里早有印证：SMART 里 M 和 A 最难写，OKR 里 KR 比 O 难写，TDD 里测试比代码难写。于是指令文件越来越厚，反馈环节始终薄弱。

**判据**：
- 你在给指令文件加规则、加说明，而同类的错误仍然出现——最直接的信号：写前馈没解决问题，缺的是反馈。
- 统计指令文件里的控制项：要求 agent"怎么做"的条数远多于"检查什么"的条数。
- 工作流程里没有"自动检查"这一步。

**处方**：**反馈优先（Feedback First，12 讲）**——需要新增一条控制时，先写它的检查形式，而不是过程规则形式。同一意图两种写法：`亮点必须有数据` 是前馈，`检查亮点部分是否包含数据` 是反馈。

为什么先写反馈（12 讲给出了三条理由）：
1. 检查在循环的反馈环节，agent 每次都会走到；规则在前馈环节，可能扫一眼就过去。
2. 检查结果是证据：通过说明真的做到了；规则只提高概率。
3. 先写反馈会自然抑制前馈膨胀——写了检查就不必再写同义规则。

重构做法：盘点现有规则，区分前馈与反馈；让模型把前馈逐条改写成检查（"必须 X" → "检查 X 是否成立"）；一次改写不出来的，让模型扮演苛刻的面试官连续追问，直到"什么叫有数据"这类细节被澄清。**反馈不一定是脚本**：字段完整性、格式校验写成脚本更可靠；需要语义判断的（句子是否通顺、亮点是否有数据）留给 agent 判断。

**常见误判**：不要把它当成"出问题后再做的重构"——它是默认最佳实践。从第一条控制开始就用检查形式，成本几乎一样，却从一开始就有证据链。也不要把"反馈优先"误解成"全部计算化"。

## 7. 反馈过载（Feedback Overload）— 13 讲

**症状**：agent 花很长时间调最终结果，"看起来在动，但没有方向"——改好这条破坏那条，来回横跳。

**成因**：验收要求过多过细且**没有分级**，全部以同等权重交给模型。分级其实一直存在我们心里（哪条不改就返工、哪条差不多就行），却没写出来。agent 无法判断"足够好"，只能把每条都当硬标准：要么用力过猛、注意力摊薄，要么随机取舍。它甚至会把任务目标忘掉。

**判据**：
- 一次验证同时报出大量失败项（测试 23 个、lint 47 处、类型 12 个），agent 随机修。
- agent 修改记录显示它在多个信号之间反复横跳。
- 验收清单是平铺的一列，没有优先级分组。

**处方**：**分级反馈（Grade Feedback，13 讲）**。第一原则：**成功静默，失败才输出**——全过时输出一句话或什么都不输出，避免用大量"通过"稀释失败信号。第二是按严重程度分级，三档已经够用：

- **阻塞级（Blocking）**：不修就无法工作/交付，最高优先级，输出完整信息，最醒目。通常只有一两条。
- **警告级（Warning）**：应该修但不阻塞，摘要输出，需要 agent 给出评估值（例如"当前 650 字"），由人决定是否继续完善。
- **信息级（Info）**：可忽略，默认静默；这类通常可以直接转成前馈。

改写形态：把验收清单从平铺改成按优先级分组，agent 的自我矫正就有了方向——先保阻塞级，再处理警告级，信息级顺手做。

**常见误判**：分级不是"越细越好"。三层已经够：阻塞级划出必须完成的线，警告级需要模型评估，信息级通常转前馈。分更多级只会让 agent 还要花力气区分级别，等于把反馈过载换个形式再来一次。也不要把分级理解成"减少 Sensors"——Sensors 数量不是问题，权重不清才是。

## 8. 上下文倾倒（Context Dumping）— 14 讲

**症状**：agent 处理任务时间很长，过程里全是信息查找动作——检索代码库、交叉比对文档，真正动手的比例很低。改个按钮却把部署文档也读了一遍。

**成因**：两个硬限制——**上下文窗口有限**（关键信息被挤出窗口、被截断或压缩）与**注意力稀释**（信息越多，模型对不同信息块的注意力越分散，对指令的响应质量下降）。根源是上一轮"上下文工程"的惯性：下意识觉得信息多给总没错。

**判据**：
- 查看执行过程，检索/比对类动作占比很高，实际产出动作很少。
- agent 在处理明显与当前任务无关的内容（它分不清哪些相关，只好都查一遍）。
- 常驻入口文件或一次性注入的素材体积远超任务所需。

**处方**：**上下文预算（Context Budgeting，14 讲）**——把上下文当珍贵资源，按投入产出比规划。四种手段各有分工：

- **筛选**：决定"给不给"。判断标准是相关性："这段信息不给，agent 会做错决策吗？"不会就不给。最有效也最费人。
- **分层**：决定"怎么组织"。按项目层（背景、架构约束）、任务层（流程控制、具体上下文）、执行层（工具、约束、前馈反馈）分开，通过子 agent 或 skill 获取对应层。
- **按需加载**：决定"什么时候给"。入口只放核心规则和路径指引，为资料建**索引**，走一步加载一步。这就是渐进式信息披露（05 讲）。索引必须准确且跟着更新，写错主题就会读错资料。
- **压缩**：决定"以什么形式给"。长资料变摘要、完整文档只给相关片段、日志只给结论。可以压缩参考资料、日志、历史对话；**不能压缩约束与验收标准**。压缩会丢信息、也可能概括错，越重要的资料越要保留原文。

重构顺序建议（14 讲）：**从按需加载开始**建索引 → 再压缩（先让模型总结文档、提炼 API 契约与组件树）→ 之后分层 → 最后筛选。

**常见误判**：不要与 15 讲的上下文焦虑混为一谈——倾倒的成因是信息组织方式，焦虑的成因是接近窗口上限时的模型内在退化。倾倒靠整理信息缓解，焦虑主要靠双层循环造出上下文边界。也不要把"压缩"当成万金油：压缩本身可能出错，且会丢细节。

## 9. 上下文焦虑（Context Anxiety）— 15 讲

**症状**：任务初期 agent 仔细核对、做完一步检查一步；到后期上下文接近上限，它不再细致，做完一步就宣布完成，结果明显比前期粗糙。

**成因**：**这是模型自身的缺陷，无法通过指令修正**。两个可信推测：一是模型对上下文余量的感知来自训练经验的内在"感觉"，不是对实际占用率的测量——标称一百万窗口的模型可能跑到二十万就"觉得"快满了；二是上下文越长，早期内容在注意力中的权重越低，"任务还没完成、还有哪些约束"的感知变弱，收尾倾向压过继续干的倾向。表现是策略从"把任务做完"切换到"尽快结束"。

**判据**：
- 同一任务，前期质量明显优于后期，且后期跳过验证步骤、选简单方案。
- 会话上下文占用接近窗口上限时有此表现。
- 区分于惰性生成：给足上下文余量跑同一任务，表现正常即为焦虑；用同一个任务测试余量充足时是否正常即可区分（15 讲）。

**处方**：**双层循环架构 + checkpoint + 内层上下文预算（15 讲）**。
- **外层**：在 PDCA 的 Check 环节加入 checkpoint——每转一圈把当前上下文压缩存档，落盘文件。关键决策及理由、验证记录、未决事项必须**原样**保留，不能只留摘要；过程性内容压成摘要即可。需要时才由人（或内建机制按轮次）清空上下文、指定某个 checkpoint 继续。
- **内层**：严格执行上下文预算（筛选、分层、按需加载、压缩）。读大文件前先检索定位只读相关段落；入口只放索引与摘要；给单次读取设预算。子任务本身就需要大量资料时，用 subagent 把它切出去，各自有独立上下文，只把结果摘要带回主循环。

关键区分（15 讲）：压缩丢掉的应当只是过程，不是依据。决策理由、验证记录、未决事项丢了，一旦焦虑发生就无法恢复，只能从头执行。

**常见误判**：不要试图用提示词告诉模型"上下文还很空"来缓解—— 15 讲明确指出，即使把实际状况告诉模型也无法缓解。也不要等到出问题才做：这套做法应当作为默认实践，从一开始就构造进双层循环，因为焦虑不挑任务规模、且一旦发生往往要重做已完成的步骤。

## 10. 跨会话知识丢失（Cross-Session Knowledge Loss）— 16 讲

**症状**：用户已经裁决过的事，换个任务场景又冒出来。你说过"不要用某个类库"，换个环节它又被引入。

**成因**：现有两条同步通道按产物类型设计——进度走 progress（由外层读取调度）、成果走交付物（内层交回外层）。而**执行中发现的新知识、用户对话产生的判断、做过的决策**，既不属于进度也不属于交付物，归不了类就没有渠道；没有渠道，会话一结束就随上下文消失。多会话是常态架构（外层/内层、skill 与 skill 之间），所以这个坏味道频发。

**判据**：
- 不同任务产出的结果严重不一致；用户反复纠正同一件事；同类返工反复发生。
- **事前判据**：只要内层循环存在用户交互，就该做这个重构——用户随时可能表达偏好，等不一致出现再补，中间丢失的知识已经造成返工。

**处方**：**动态知识更新（Dynamic Knowledge Update，16 讲）**。先给知识分类，因为来源不同、产生时机不同：

1. **用户统筹（user triage）**：依赖用户输入，是优先级与偏好的表达，不构成定论。记录：内容 + 适用场景 + 来源（用户）。
2. **发现（discovery）**：模型执行中自己对照出来的事实。记录：内容 + 来源（执行）+ 时间。
3. **决策（decision）**：模型自主做出的或用户裁决的。记录：结论 + 理由 + 适用范围 + 来源（用户/模型）。

落成两步：内层操控循环在**任务收尾增加知识记录环节**（交付结果之前先清点本轮知识）；外层循环做**知识更新**，把条目归位到该去的地方。为什么必须在外层：只有外层知道知识在整个 harness 里的布局——决策进 ADR 目录还是规则文件、领域知识对应哪份文档、用户偏好归哪个文件。内层只知道本轮发生了什么，让它自行决定往哪写会让逻辑过于复杂。

**常见误判**：不要以为"同一个聊天窗口开多次"就是多会话——真正的多会话由 harness 结构造出，各自有独立上下文与生命周期。也不要把知识记录塞进 progress 文件：那会同时污染状态（见下一条）。

## 11. 状态污染（State Pollution）— 17 讲

**症状**：状态里出现"这一次执行"的痕迹——某次练习的正确率、某次工具返回的中间结果、某次会话里的临时结论——后续会话把它当长期事实使用。

**成因**：单 agent 架构下，一个会话既要执行又要记录，共享同一个上下文；调试痕迹、中间产物、临时判断、幻觉与要长期保留的进度、决策、知识之间没有边界。一旦发生上下文压缩或注意力偏移，一次性数据就被混进长期状态。两个典型来源：工具给出误导性结果（计划筛选条件出错、一个词都没匹配到，却照样返回"本轮练习完成"），以及模型过度推断（一次用了某个语法就写"已掌握"）。幻觉不是被"识别"出来的，而是被"打回证据"这个动作拦住的。

**判据**：
- `grep -rnE '"(date|last_run|this_session|temp)"' state/` 出现单次执行字段。
- 同一个错误结论在多个会话里反复出现，被不同会话轮番当成事实。
- 进度状态可以被内层执行环节直接写入（没有经过外层核验的通道）。

**处方**：**状态分区（State Separation，17 讲）**，按生命周期分成"随任务消亡的临时状态"与"跨会话复用的持久状态"。两种分区方式：

- **草稿纸（Scratchpad）**：给执行数据单独划一块临时工作区——草稿、中间产物、调试观察、工具原始返回、未验证结论都写这里，任务结束随草稿纸销毁。但草稿纸里也混着值得保留的东西（用户偏好、发现的事实、做出的决策），所以收尾要先做**整合（consolidation）**：对每条内容重新判断"这是知识还是执行数据、依据是什么"，提炼成带来源的知识条目，剩下才销毁。整合不只是挡污染，也是对进度执行的复查——工具说"完成"，对照进度表一核就能发现其实没有复习记录。
- **双层循环**：会话边界把执行数据关在短命会话里；状态的唯一主人是外层（内层没有直接写持久状态的通道）；审视者与执行者分离；Check 环节天然就是整合点。

**常见误判**：出现状态污染，实际表明**任务复杂度已经超过当前 harness 架构能处理的范围**。与其只想着治污染，不如先检查架构与任务是否匹配。单一类多任务可用草稿纸模式；多种任务协作时，直接上双层循环。不要以为加一条"不要写错状态"的规则能解决——根源是没有边界，不是态度问题。

## 12. 环境漂移（Environment Drift）— 18 讲

**症状**：昨天能跑今天不行，代码、提示词、状态都没动；或者同一任务跑两次结果不同，复现不出来；或者"在我机器上跑得很好"。

**成因**：agent 运行依赖的、又不在它自己控制范围内的外部条件没有被显式声明和锁定，却在悄悄变化。四类：**运行时**（OS、语言与版本、shell）、**依赖**（第三方库及精确版本）、**外部服务**（API、数据库，会改版且通常不通知你）、**模型**（同一个名字背后静默滚动到新版本）。漂移分两种：时间上的（API、模型改版）与空间上的（依赖、shell、OS 因机器而异）。

**判据**：
- 存在 `init.sh` / `setup.sh` 等初始化入口，且能从确定状态开始（而不是"这台机器当前的系统状态"）。
- 存在 lockfile（按语言选 `.nvmrc`、`package-lock.json`、`requirements.txt`、`pyproject.toml` 等）。
- 第三方 skill 是否在项目内并被 pin 到 tag 或 commit；有没有从全局目录加载的第三方 skill。
- 外部 API 调用是否经过间接层（如 MCP 服务器），还是 agent 直接拼调用。
- 换一台机器 clone 后跑初始化，行为是否一致。

**处方**：**环境锁定（Lock Environment，18 讲）**，用的是软件工程里成熟的 lockfile 范式：
1. **环境初始化**：用 `init.sh` 固定文件夹结构、配置文件与初始状态。
2. **锁版本**：用 lockfile 锁运行时与依赖精确版本。
3. **第三方 skill 局部化并 pin**：落到项目内 `skills/third-party/`，锁 tag 或 commit，与项目一起进版本控制；在 AGENTS.md 写两条规矩（第三方 skill 必须装在项目内并锁版本；只加载项目内的 skill 与内建的，不认全局目录里装的）。加一道检查：跑初始化时校验实际内容与锁定版本一致，不一致就报错停下。
4. **外部服务用间接层吸收**：agent 不直接调外部 API，而是经 MCP 服务器；外部改版时只改适配层。MCP 服务器同样局部化、固定版本、进版本控制。
5. **整包分发**：完成局部化后可打成 Docker 镜像，换台机器、换个人跑起来就是相同环境。

**常见误判**：`init.sh` 与局部化 skill 应当作为默认实践，不要等症状出现再补——漂移没有预警，等发现"昨天能跑今天不行"时再想找回"昨天用的哪个版本"非常痛苦，而这两件事成本都很低。也不要指望用 agent 的自我纠正机制对着报错去自愈生产环境的 API 变更：不推荐在生产环境打猴子补丁。

## 13. 模式复制漂移（Pattern Copy Drift）— 19 讲

**症状**：你在 AGENTS.md 里写下了新约定，agent 新写的代码形状却和仓库里最想淘汰的旧模式一模一样。同一句评审意见在多个 PR 上重复出现。

**成因**：仓库里既有的产物本身就是 agent 的学习材料，它会复制读到的模式，不管这个模式是否正要淘汰。三条原因：训练目标是"给定上下文预测下一段代码"，奖励的是"接得像"而不是"判断得对"；**指令与范例冲突时范例权重更高**——你写下的约定只有寥寥数条，仓库里可被模仿的旧实现却成百上千；agent 写代码前先检索同类实现并按相关度排序，排在前列的正是旧代码。

**判据**：
- 新代码和打算改造的老代码长得一样。
- 同一条评审意见在多个 PR 上重复出现。
- 只有约定（前馈），没有任何会失败的自动检查来拦旧模式。
- 只需存在重构或改写，就会出现漂移；遗留系统改造是高发场景。

**处方**：**模式基线化（Pattern Baseline，19 讲）**，四步，顺序有依赖：
1. **正向范例**：针对要解决的问题给一份参考实现，放在仓库固定位置（如 `references/`），在 AGENTS.md 里指路。建议用独立的参考文件，不要指向项目里会被改动的实际代码。写不出范例时，找一个独立的外部参照。范例一旦定下，它就是"什么算标准"的唯一答案。
2. **确立架构约束**：让"照旧样例写"失败。用自定义 linter 或架构测试（如 ArchUnit 风格的检查）把约定变成会失败的自动化检查。原则是**强制不变量，不微观管理实现**：可以要求"业务逻辑不得出现在 controller"，但不规定 service 方法怎么切。
3. **建立基线**：先跑一次约束，把现存违规全部记入基线文件；之后只许减少不许增加，有新增违规立即停下修复。明确承认现状不完美，但不接受变得更差。
4. **持续清理**：任何一次改动只要碰到存量代码，就在这次改动里按新模式重写。不需要额外努力——约束会告诉 agent 现在不符合新模式，范例会告诉它该怎么改。

四步缺一不可：先有范例，约束才拦得对（只堵旧的不给新的，agent 无路可走时会就近抄一个）；先有约束，基线才有东西可记；先有基线，约束才敢上线（存量处处违规时 agent 根本干不了活）。

**常见误判**：不要以为"把约定写得更详细/更强调"就能解决——范例在数量上占压倒优势，加强指令收效有限。架构约束也不必一次设计完，用知识固化一轮轮长：每次 agent 犯一个新的架构错误，或评审里出现一条新的重复意见，就问一句"这条能不能变成一条检查"。

## 14. 技能触发不一致与体积失控（Skill Trigger Drift & Bloat）— 20 讲

**症状**：该用某技能时没被选中，或两个技能之间反复摇摆；技能越来越胖，执行时"失去注意力"。

**成因**：技能的意义是从随机系统里挤出确定性，判据是**可预测**——每次跑出类似的过程，而不是相同的输出。两类不一致：**触发不一致**（该用时不用），根因在 description——它是唯一常驻上下文、也是唯一的竞争位，却常被写成"这个技能能干什么"而非"什么时候用它"，多个技能描述还容易撞车。**体积失控**：技能会自己变胖，而单纯设"不超过 500 行"并不是最好的控制方法。

**判据**：
- 读每个 SKILL.md 的 frontmatter：description 是否给出触发场景，是否有"不要用于"的边界句。
- 把所有 description 并列，看是否存在语义几乎相同的技能对。
- 技能这次列提纲、下次写全文，第三次又改格式——过程不稳定，即使结果都还过得去。
- 四个环节是否缺失（缺失比臃肿更常见）：Guides / Action / Sensors / Steering。
- 正文是否超过约 500 行 / 5000 token 的实测拐点。

**处方（20 讲）**：
- **description 写"何时用"**：例如写"当用户提到"本周进展""周期性汇报""汇总一下情况"，或者到了固定汇报节点时使用"，而不是"这个技能能帮用户写汇报"。两个技能撞车时，各自把"不该用在哪儿"写进描述。
- **模型调用 vs 用户调用**：带 description 的是模型调用技能，可由 agent 自行推断触发；需要人明确指定才触发的，把 description 摘掉，变成用户调用（消除模糊性，代价是认知负载全压在人身上，别的技能也叫不动它）。
- **恰当的自由度**：量的是内层四环节里有多少交给模型——低自由度把四环节全部定死、模型只负责执行 Action；中自由度把 Guides 与 Sensors 固定下来、把 Action 里的选择留给模型；高自由度只给方向与标准。选哪一档看"这一步做错了能不能倒回来"。
- **体积控制先结构后数字**：先查四环节缺不缺，再看膨胀发生在哪一环（前馈在膨胀，就是前馈痴迷；反馈在膨胀，就是反馈过载）；Action 膨胀通常是逐字命令写得过多，机械重复的操作应收敛成脚本调用；Steering 膨胀通常是异常分支铺成了决策树，只留几条关键转向（何时停、何时重试、何时升级给人）。结构没问题之后才看行数与 token。
- **拆分依据**：能否提取一个**独立的触发器**；拆出来的技能必须自己有完整的四环节。只有 Action 的只是被挪走的一段说明；只有反馈的，说明它应该是分级反馈里的一步。

**常见误判**：不要用"行数达标"当健康标准——数字量的是总量，不是分布；四个环节缺失比臃肿更常见。也不要把"高自由度"当成"写得不认真"：不同任务对确定性的要求不同，过度限制等于拿写代码的思路写技能，会造成不必要的限制。
