# ask-flow — 该用哪个技能

你想不起来这一堆技能各自管什么，所以问。

这是一个路由：说清你现在的处境（一个还没成形的想法、一堆进来的 issue、一段调不通的代码、一次漫长的实现），它挑出该走的那一步，**然后直接开始**——读那个技能的正文并按它做，而不是只报一个名字让你再敲一遍。

只有两种情况停下来问：两条路真的接近（比如这批 issue 到底算并行还是串行），或者下一步越过人的判断边界（开 PR、合入、产品验收）。其余情况自己走下去——把每一步都变成「请确认」，等于把该由 agent 做的判断推回给人。

## 主线：想法 → 交付

大多数新功能走这条。

1. `/prd` — 把想法逼成需求文档。只有一个模糊念头就从这里开始；它会追问到"能写进验收条件"为止。需求已经写清楚了就跳过它。
2. `/to-design` — **只在触发条件命中时**：跨两个及以上服务、改数据模型或迁移、涉及两条以上对外契约。写的是重"为什么"与权衡的设计提案（Markdown 是主产物，HTML 只是可选的呈现层）。不命中就跳过——单服务单接口的字段扩展留 PRD 加远端契约即可。
3. `/to-issues` — 拆成垂直切片（每条都能单独演示）并写清真实的 blocking 边，创建到 GitHub 或本地。**每条 issue 的正文就是契约**：目标、非目标、验收条件、必须收集的证据、外部边界、完成定义、未决问题都在正文里——所以没有"先写一份 SPEC 文档"这道必经步骤，写不写设计提案由上一行的触发条件决定。
4. 岔口：这批 issue 之间是什么关系？这一步选错，后面全是浪费。
   - 真并行（互不共享逻辑/文件）→ `/graph`：每节点独立 git worktree、按波 fan-out、波级一次集成一次评审一次交付。
   - 有依赖、基本串行，或干脆就是一条链 → `/loop-it`：一次一个、`.loop-state.json` 检查点、崩溃可恢复。
   - 只有一两个单元、共享文件，或只是链 → 都别用：走 `/implement`（内联实现 → 门禁自证 → `/review-it` → `/ship-it`）。上图和开循环在这三种情况下只会多付编排成本，而并行度并不会增加。
5. 执行（不管上面哪条）：实现 → 用项目自己的门禁自证 → 过 supervisor 检查 → 只 commit。节点/单个 issue 都不 push、不开 PR、不自审——评审要留给一个没写过这段代码的读者。设计决策/偏离/权衡由 `/ship-it` 的实现总结评论承载一次，不需要另开一份笔记。
6. 收批 / 收波（各只做一次）：`/review-it` 审集成后的完整 diff（重点是节点之间的结合部）→ `/walkthrough` 交出证据（命令与真实输出、可视化、风险点、人工验收状态）→ `/ship-it` 开一个 PR、合入、关闭满足的 issue。走查件**只提供证据，不产 PR body**；PR body 与合并清单归 `/ship-it`，它是唯一产出者。

## 岔路：从别的入口进来

- 有 bug、偶发 flake、性能回归 → `/diagnose`。它的纪律是：在有一条已经在「这个」bug 上变红的命令之前，不许开始推理；之后是最小化复现、写 3–5 条可证伪的假设、一次改一个变量地埋点、在正确的接缝上补回归测试。它不做 review/ship——定位清楚后按第 3 步回主线。
- 一堆别人提的 issue、原始 bug 报告 → `/triage`。它把外面的条目分流成 `ready` / `needs-info` / `bug-confirmed` / `duplicate` / `wontfix`，并把 `ready` 的补成 agent 可执行的卡片。`/to-issues` 产出的卡片不要 triage——那些已经 agent-ready。
- 想先把行为定下来再写实现 → `/test-first`：红 → 绿，一次一个接缝；`/implement` 内部就会用到它，也可以单独调用。
- 正在解 merge / rebase 冲突 → `/conflict`：查清两边意图后逐 hunk 解，跑项目门禁，永远解、不 `--abort`。它独立于所有流程。

## 维护：不是新功能，只是让代码库保持可维护

- `/refactor` — 两种模式：`audit` 只报不改（架构坏味道、复杂度热点、反模式，按严重度出报告），`fix` 默认（按 Fowler 目录做不改行为的重构）。
- `/modern-go` — Go 版本化的现代化改造（读 `go.mod` 决定规则集）。
- 两者是一条线：`/refactor audit` 找到候选 → `/refactor fix` 或 `/modern-go` 动它。找到的"这里缺一个好的接缝"往往本身就是一个新 issue，可以并回主线。

## 理解与产出

- `/understand` — 把这次改动变成可交互的审阅网页（左树右 diff + 逐段解释），主要给人看。
- `/svg-diagram` — SVG 制图规范与机械校验：先按它的图表类型清单定图型，再按布局 / 连接线 / 箭头 / 配色 / CJK 字体栈的规则画，最后跑 `tools/svg-lint` 的 12 项检查。**图画完必须过 lint**，不要靠肉眼。

## 最容易误用的七个边界

1. 链不要用 `/graph`。A→B→C 这种"每一步等上一步"的形态是链，用 `/loop-it`：`/graph` 的价值全部来自波内节点真独立，链只会把它退化成带额外仪式的串行。
2. 一个单元不要开循环。单点改动就是 `/implement`（内联 → 门禁 → `/review-it` → `/ship-it`），这也是技能里写着的默认。
3. 单节点波不建波分支。波里只有一个节点时没有可集成的东西，直接拿该节点分支评审与交付。
4. 节点不自审，但**单个 issue 有 supervisor 检查**。`/graph` 的节点契约止于 commit，评审是波级一次（按节点分节过，重点看节点之间的结合部）；`/loop-it` 每个 issue 实现完过一次 supervisor 检查，判据是证据而不是 diff 观感。节点级 PR 是"昂贵模式"，用户明确要求才用。
5. 一批多 issue 共用一个 PR 时必须逐项列证据（commit / 关闭的 issue / 验证测试名 / 人工验收状态），否则 squash 之后无法单独回滚或审计。
6. 还没有会变红的命令时，不要开始猜假设。这是 `/diagnose` 存在的全部理由：先有环路，再有理论。
7. 不要 triage 自己拆出来的卡片。`/triage` 只管从外面进来的原始条目；`/to-issues` 的产物已经 agent-ready。

## 上下文卫生

"在哪个窗口里做"和"用哪个技能"同样重要：

| 情况 | 怎么做 |
| --- | --- |
| 一个单元、要在几轮里来回判断 | 内联做（`/implement`），不要开子代理 |
| 独立、自包含、你能把验收条件写清楚 | 派发一个**全新子代理**，一条自包含提示词 |
| ≥2 个真独立单元，且风险在集成处 | `/graph`：一波 2–3 个节点，波间有 fan-in 屏障 |
| 一串有依赖关系的 issue，要能崩溃恢复 | `/loop-it`，检查点落 `.loop-state.json` |

三条硬约束，违反了会静默出错：节点必须用绝对路径（子代理没有自己的 cwd，相对路径会改到编排者的检出）；共享检出必须始终干净（编排器据此做泄漏检查）；长构建/测试作为后台任务运行。节点停摆先用追加消息**让该子代理继续**（原地重试），再换新节点，再考虑剔除——它的兄弟节点本来就相互独立，不必陪等。

## 前置条件

流程假设三件事成立，否则门禁与泄漏检查都是空的：仓库有一个真实可跑的门禁命令（例如 `mise run check`）；工作树状态文件（`.graph_state*`、`graph.html`、`.loop-state.json`、`nodes.json`，按次自定义的名字也算）已进 `.gitignore`；`gh` 已登录（`/ship-it` 用它开 PR）。

## 维护规则

任何可被用户触达的技能被新增、改名或删除后，必须回来重读并更新这个路由——否则它会给出一条指向不存在技能的路线，而说谎的路由比没有路由更糟。同一件事还要同步到 `README.md` / `README_EN.md` 的技能表，以及 `docs/index_cn.html` / `docs/index_en.html` 的对应小节。
