# 走查件 —— 交付前证明这次改动

实现和它的验证一过，写一份 Markdown，让**没看过这段工作的人**追上**改了什么**与**证明了什么能用**——评审者、下一个接手的人、几周后的你自己。

**工作状态、证据层、产物落点见 [`../../CONTRACT.md`](../../CONTRACT.md)——本文件不复述。** 这里只写走查件本身：它给谁看、多长、承载哪一层证据、哪些不算证据。

重点在 evidence，不在断言。diff 说的是代码长什么样；走查件说的是你跑了什么、它打印出什么、你看到了什么。

**它是投影，不是第二份真相。** 每条验收条件的机器真相在检查点（`<scope>/issues/.loop-state.json` 的 `evidence`，含 `--layer`；`/graph` 那边没有 per-criterion 的 `evidence`，靠 fan-in 核 `gates`/`files` 与集成后的门禁）。走查件引用它们，写给没跑过那些命令的人看，不另存一份机器记录。

## 多长

**每份 ≤ 30 行。** 一条命令 + 关键输出 + 截图路径。**原始输出倾倒不是证据，是噪音**——要留完整输出就给路径，不贴进来。宁可要 2–4 张能证明路径的图（前 → 动作 → 后），不要一堆截图。

## 哪些不算证据

| 看起来像证据 | 为什么不是 |
|---|---|
| 几百行原始输出 | 读者要的是「哪条验收条件、哪一层、什么命令、结果如何」；倾倒把结论埋掉了 |
| 「测试通过」四个字 | 观测是**命令 + 结果**；没写命令就没法被证伪 |
| 覆盖率数字 | 只说明某一行被执行过，不说明它的影响被验证过 |
| 静态截图 / 「看代码觉得对」 | L3/L4 的证据是真的把跑起来的东西点一遍 |
| 未验证的断言打勾 | **绝不把未验证的断言变成一个勾选框**；跳过的步骤要明说 |
| 没人核对过却写「已人工验收」 | 如实写「尚未人工验收」——它是标注，不是闸门 |

## 什么时候写，什么时候不写

**范围：每批或每波一份——与评审、交付同一个范围，绝不逐 issue 一份。** 逐 issue 的走查证明的是一份可能活不过集成的 diff，而且每个都要付一轮截图；一批或一波只有一个 PR。逐 issue 的**理由**由 `/ship-it` 一次交付；逐 issue 的笔记文件是仓库自选的约定，不是默认步骤。

- 写：实现与它的验证一过，项目门禁是绿的，`/review-it` 已经跑过，`/ship-it` 交付之前。
- 不写：**一行改动或纯机械改动**（没有演示路径也没有可追的东西，直接把 diff 递过去）；**单单元路径**（契约 §3）；**评审之前**（给一份马上要改的代码写走查，等于写一份还得重写的走查）。
- **它记录门禁输出，不替代跑门禁。**

## 谁来做：内联还是子代理

这份产物要读很多东西——完整 diff、每条命令的原始输出、要截图的演示路径——而且是一次性的：写完就交出去。**批末或波末尤其该派子代理**：那时编排者的上下文已经装了一整批实现过程，正是最该省的时候。

派的时候提示词必须自包含（子代理看不到这段对话）：diff 范围、要证明的验收条件、**你实际跑过的命令与原始输出**（这是它唯一拿不到、也最要紧的原料——要么贴进去，要么给它一个能读到的路径）、演示路径怎么复现、落点与格式。**证据得由你交过去**：子代理不替你重跑命令，它只把证据写成一份经得起看的走查件。

**产物写完才能交付，所以传 `run_in_background: false` 等它回来。** DSH 的 `subagent` 默认后台跑，而后台子代理不会让本回合保持忙碌；以「等它返回」结束回合就是 `turn_end: completed`，在 headless 里整个运行到此结束，走查件与它后面的交付都不会发生。

## 逐节写什么

**1. 变更摘要**——写给没看过这段工作的人。读 diff 与它服务的 issue / PRD，3–6 条说清建了什么、改了什么、删了什么，点名关键文件与新增部分的形态（模块、端点、数据结构），并链上 issue / PRD。

**2. 验证步骤**——你跑了什么，它打印了什么。跑项目门禁（或针对性子集），贴准确命令与真实输出（噪声可截掉，通过数要留）；有界面就驱动演示路径，每步记成 动作 → 观察到的结果 → 通过/失败。**每条验收条件写清它那一层的证据**，缺层如实记录，不用推断补齐；跳过的步骤要明说，绝不藏起来——仓库里没有测试、没有 UI 可驱动就直说。

**3. 可视化证明**——演示路径的截图或短录屏，让读者看到行为，而不是相信一句关于它的话。网页用浏览器自动化（`npx playwright screenshot <url> tasks/shot.png`），macOS 抓窗口用 `screencapture`。**默认相对路径** `![caption](tasks/shot.png)` 并把图片一起 commit，保持小；**只有产物必须独立存活时才用 base64 data URI**（粘进聊天、issue 评论），并说明用了哪种——base64 的走查件有若干 MB，应当是一个刻意的选择。没有可视界面就写 "None — backend/CLI only"，不要硬凑。

**4. 评审门禁**——读者合入前要核对的东西：`git status` / `git diff --stat HEAD` / `git diff --name-status` 的 diff stat 与文件清单、高风险说明（force-push 过的历史、迁移、配置改动、大范围重构）、以及**如实**的人工验收状态。

**PR body 与合并清单不在这份文件里产出**——它们是 `/ship-it` 的产物，由它写一次；走查件只负责证明，`/ship-it` 直接引用这份证据。

## 模板

存成 `<scope>/notes/walkthrough-<feature>.md`（kebab-case；作用域根见契约 §8）。功能名：用户给了就用；否则从需求分支 `feat/<scope-slug>` 去掉前缀推；`documents/` 里有 PRD/SPEC 就复用它的功能名；都不行就问。

````markdown
# 走查 — {功能 / issue 标题}

> 生成于 {date} · 分支 {branch} · {commit 区间}

## 变更摘要

{2–4 句话，写给没看过这份改动的人}

- {建了什么 / 改了什么 / 删了什么}
- {关键文件、组件、端点、数据结构}
- {它满足的需求——链上 issue / PRD}

## 验证步骤

| 验收条件 | 层 | 命令 / 动作 | 观察到的结果 |
|---|---|---|---|
| {条件} | L3 | `{准确命令}` | {ok 行 / 通过数} |
| {条件} | L4 | {演示步骤} | {发生了什么} ✅ |

_{跳过的步骤与原因；没有 UI 就写 N/A}_

## 可视化证明

![{caption}](tasks/{shot}.png)

_{或：None——仅 backend/CLI}_

## 评审门禁

```
{git status / git diff --stat HEAD / git diff --name-status 的输出}
```

- **高风险**：{force-push 过的历史 / 迁移 / 配置改动 / 大范围重构——或 None}
- **人工验收**：{谁在什么时间 / 环境验过，或「尚未人工验收」}
````

## 边界情况

| 场景 | 处理方式 |
|---|---|
| 什么都没改（`git diff` 为空） | 直说；不要编一份走查件出来 |
| 没有自动化测试 | 注明 "no automated tests in repo"，靠人工 / UI 证据 |
| 没有 UI 界面 | 可视化证明 = "None — backend/CLI only"；UI 行 = N/A |
| 图片无法内嵌 | 退回相对路径，并列出要一起 commit 的文件 |
| 这个功能已经有走查件 | 默认覆盖（一份新的快照）；要就地更新就先问 |
| 验证没能完成 | 记成 blocker——绝不把未验证的工作标成已证明 |
