# 下一步：重建 eval 体系

**起点状态**：仓库干净，`make check` 与 `make test` 全绿，master 已推到 `fbf4e67`；技能装到
`~/.agents/skills`，与仓库逐字一致。注意 `npx skills add` **只加不删**——删掉技能后要手动清安装目录。

现有 eval 是 `evals/harness`（Go，`evalctl`）：8 个 fixture 用例 + 24 条触发用例，`bench` 汇总，
结果落 `evals/results/iteration-N/`。

## 三个实测出来的毛病

1. **贵到没人跑。** 一轮 8 个用例：`with_skill` 20.2M tokens / 84 分钟，`without_skill` 3.8M / 19 分钟
   ——5.3 倍 token、4.5 倍时间。改一次技能要等一个半小时才知道有没有弄坏，于是就不跑了。
2. **一半断言不区分。** 18 条断言在两条臂上都满分：它们花掉 token，什么都没测出来。
   另外 `06-exception-path`（56–100%）与 `07-parallel-waves`（60–100%）本身是 flaky 的——
   写成"通过"的用例其实在掷硬币。
   **⚠️ 2026-09-29 更正：这两条的 flaky 标签是错的。** 方差全在 **without_skill** 那条臂上：
   `06` 的 with_skill 三次 **9/9、9/9、9/9**（1403 / 1557 / 1518 s），without 是 9/9、6/9、6/9；
   `07` 的 with 两次 **10/10、10/10**，without 是 6/10、5/10。**两条用例都是稳定的好区分器**——
   "56–100%" 是把两条臂混在一起算出来的，那个数字没有意义。控制臂偶尔也能撞对仪式，
   所以真实的区分余量比表面看的小。
3. **只量结果，不量过程。** 断言看文件和探针（东西做出来没有），看不见技能契约本身：有没有开
   goal、单单元有没有偷偷建检查点、有没有停在"等你回复"上、证据有没有写清它属于哪一层。

## 重建方向：按"要花多少钱"分层

| 层 | 量什么 | 代价 | 什么时候跑 |
|---|---|---|---|
| **T0 路由** | 24 条触发用例：这句话该加载哪个技能 | 秒级，可并发 | 每次改 description、加删技能 |
| **T1 形态** | **小任务**（一句话能做完）+ 只读事件流与文件树：加载了哪个技能、调没调 `create_goal`、有没有检查点 / worktree、有没有停在等人 | 分钟级 | 每次改 SKILL 正文 |
| **T2 结果** | 现有 8 个用例的 gate / probe / tamper_guard | 小时级 | 发版前、改脚本或门禁之后 |
| **T3 对抗** | 评审与证据的质量（独立子代理逐条判） | 最贵 | 改 `review-it` 或证据层之后 |

**T1 是现在缺的那一层**，也是重建的重点：它便宜到可以每改一次就重跑，而且直接量契约。

## 第一刀

1. 加一层**小任务**用例（T1）：任务小到几十秒做完，只判过程事实；现有 8 个用例留在 T2。
   **T1 便宜是因为任务小，不是因为少判断言**——臂跑本身才是成本，判几条断言不影响它。
2. **先量区分度再留断言**：两条臂各跑 3 次，报每条断言的通过率；两边都 100% 的删掉，或者改成
   能失败的形态。
3. 补契约断言：`goal_opened`（事件流里有 `create_goal`）、`checkpoint_absent`（已有）、
   `no_human_wait`（没有以"等你回复"结束回合）、`evidence_layer`（检查点里的证据带了层）。
4. 触发用例扩到**每个技能至少两条**，其中一条是近邻——该走别的技能，或者根本不该加载。
5. 一轮跑完出一张表：用例 × 断言的通过率 + token + 时长；**flaky 的单独列**，不许把 60% 记成通过。

## 红线

- 不加只为了"更全"的断言。**每条断言都要能失败**——从不失败的传感器说明它不必要。
- 不为了让用例变绿而放宽门禁。改测试就是改契约。
- 不用 Agent Teams；并发用 `subagent` / `workflow`。

  过程断言（`skill_loaded` / `goal_opened` / `no_human_wait` / `evidence_layer`），**每条断言一条
  负例自测**（`evals/harness/events_test.go`，挂在 `make check` 上）。用例写 `"tier": "t1"`，
  现有八条缺省是 `t2`。
- **区分度**：3 用例 × 2 臂 × 3 次，**跑了两轮独立采样**（第一轮拷贝式安装、第二轮软链安装且技能正文
  含 `/merge-it`），逐用例结果完全一致：with_skill 1.00、without_skill 0.71，**36 次运行里没有 flaky**。
  按第 2 条删掉 7 条两边满分的断言（`workspace_clean` ×3、`path_absent` ×3、`tool_absent` ×1），
  留下 4 条有独立失败模式的作回归守卫。表在 `results/t1-1/benchmark.md` 与 `results/t1-2/benchmark.md`。
- **成本**：一轮 18 次臂合计约 47 分钟臂时间 / 9.6 M token，6 路并发约 10 分钟墙上时间，对比 T2 的
  84 分钟低一个数量级；单条 with_skill 270 s / 950 k token、without_skill 41 s / 116 k。

T1 顺带抓出两件事，都不是断言写错：

- **安装目录里没有 `CONTRACT.md`**——拍平不会复制不是技能的文件，臂 `read` 它得到 `not found` 后
  花好几个工具调用到处找。当时改成软链安装（`make link`）并给外人补了一条 `cp`；**后来发现那条 `cp`
  对外人根本跑不通**（`cp skills/flow/CONTRACT.md` 是仓库相对路径，而外人是从 GitHub 装的），于是
  根治：把它挪进 `skills/flow/loop-it/`，跟着技能一起被复制，`cp` 与脚本特判都删掉。
  证据留在 `results/t1-0-missing-contract/`。
- **`tamper_guard` 保护了臂本来就会改的测试文件**——卡片写着「补上对应的测试」，臂改 `greet_test.go`
  是照做。改成在 fixture 的 `AGENTS.md` 里声明**冻结基线**，测试写新文件。

**T0 触发层**：24 条 → **36 条**，自有技能（flow + bonus）每个至少两条、其中一条是近邻；自检加了
覆盖守卫与 `forbid` 校验。三轮跑下来（`triggers-6/7/8`）：31 → 32 → **34/36**。过程中修掉两个
harness 缺陷（`skillsLoaded` 把失败的调用记成加载、调用轴缺一个「绝不许加载」的断言形状）和一处
`graph` 描述对「并行」太贪；剩两条真红（`near-loop-it-shared-file`、`near-graph-chain`，都是先摸
`graph` 再转 `loop-it`）与一条 flaky（`near-trivial-function` 5/6），明细见 [README](README.md#扩到-36-条之后三轮每轮-36--3)。

**还没做**：

## 并行 profile 的 T1，与 T2 的 graph 复跑（2026-09-29）

补上三个 profile 里唯一缺的那条：**`t1-parallel`**（两个互不相干的包 / 两张卡 / 不共享文件），
判的全是编排形态——`skill_loaded: graph`、节点各自记了 `feat/` 分支、检查点与看板落在作用域根、
没有 loop 检查点、**没有合入**、没有停在等人。

**T2 的 graph 复跑**：`07-parallel-waves` **10/10 vs 5/10**（408 s / 1.9 M token）。
`graph` 正文从 303 压到 199 行、交付拆出 `/merge-it` 之后，结果层没坏。

**T1 便宜的前提是「固定仪式轻」——对 graph 不成立。** `t1-parallel` 实测 219–386 s / 689 k–1.6 M
token，对比 `07` 的 408 s / 1.9 M：**只便宜约 40%，不是数量级**。并行 profile 的成本在规划、建波、
worktree、看板、fan-in、波末交付这些**与节点做多少活无关**的固定开销上，把任务改小省不下多少。
`NEXT.md` 开头那句「T1 便宜是因为任务小」只对单单元成立。

**同一个用例、同一个臂，四次跑出 9/10、9/10、7/10**——两次 9 是**断言写错**，一次 7 是**真缺陷**：

| 错法 | 为什么错 | 改成什么 |
|---|---|---|
| `path_absent` 查 `.git/worktrees/*` | 那是**瞬时产物**：`graph/SKILL.md` 要求波末删掉已完成的 worktree，正确路径跑完本来就是空的 | 从 `.graph_state.json` 读每个节点记的 `feat/` 分支（`07` 用的同一条证据） |
| 「`main` 还停在种子 commit」 | **禁掉了一个文档要求的步骤**：技能要求第一个波之前先提交 `.gitignore` | `git grep 'func Upper' main`——直接查交付的实现有没有落到默认分支；精确覆盖 merge / squash / fast-forward，也不受那条提交影响 |

两条都**先证明能失败**再收（在 materialize 出来的 fixture 上造正确态与违约态各跑一次）。
教训：**T1 的断言只能挂在「跑完之后仍然存在、且技能正文要求它存在」的东西上**——瞬时产物和
「什么都不许发生」都写不出稳定断言。

**那条真缺陷**：graph 编排全对（节点分支、波分支、worktree、fan-in 合并都在），但
`.graph_state.json` / `graph.html` / `nodes-*.json` 落在了**仓库根**。逐条看那次 28 次工具调用，
臂**从没读 `AGENTS.md`**——于是不知道仓库声明的 `## 作用域根` 是 `requirements/<scope>/`，
`ROOT="$(git rev-parse --show-toplevel)"` 一路把产物放进仓库根。既不是默认值也不是仓库的约定，
而且没有任何东西会报错。修在 `7ac85a3`：CONTRACT §8 加「作用域根要读出来，不要猜」，
`graph/SKILL.md` 写明「仓库根不是作用域根」并把 `$ROOT` 的含义点明。

**成本方差要当区间用**：同一条用例、同一个臂，with_skill 219 / 255 / 341 / 386 s，
689 k / 949 k / 1.4 M / 1.6 M token。**而且跑得最便宜的那次正是唯一出错的那次**——快，可能是因为
跳过了该做的读。引用成本时别写定值。

**修完复跑：10/10**（341 s / 1.4 M token）。`t1-parallel` 是四条 T1 用例里唯一覆盖并行 profile 的，
它抓到的那条缺陷修完已经回到绿。

（`06` 的 with 取三次中位数，旧值取 iteration-11/12 均值；其余旧值取 iteration-14/16。）

**三条结论：**

1. **重写没弄坏结果层。** 八条分数与重写前逐条相同，`04` / `05` / `08` 仍然区分
   （with 满分、without 差一条）。`07` 的 without 从 6/10 掉到 5/10，在它自己的波动范围内。
2. **墙钟普遍翻倍，token 却没有。** 七条 with 臂里六条时长涨（中位数约 2×），而 token 有涨有跌——
   `02` 的 token 降 37% 而时长涨 89%，`07` 的 token 降 32% 而时长涨 17%。
   **时间和 token 反向移动，说明涨的不是"活"，是每一步的延迟。**
   所以这条**不能归因于技能重写**；要坐实得控制变量重跑（同一份技能、同一时段跑两遍）。
3. **`06` 的历史基准（470–500 s）作废。** 这次 1403 / 1557 / 1518 s。引用旧 timing 前先看测量条件。

**`01` / `02` / `03` 两条臂都满分——T2 里它们不区分。不删**：T2 的职责是回归网
（with 臂掉分就是警报），区分度是 T1 的职责。真要砍，砍的是「断言」那一层，不是用例。
